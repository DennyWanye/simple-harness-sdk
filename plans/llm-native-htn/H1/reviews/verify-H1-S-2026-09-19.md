### P1-1 — 规定变异「binding_hash 少算一项」存活，且缺省文档的 binding_hash 无人验证（测试缺口）

- 位置：`src/agent_orchestrator/orchestrator/planning_protocol_binding.py:52-55`
  （`planning_protocol_binding_hash`）与 `:70-78`（`PLANNING_PROTOCOL_BINDING`）。
- 事实：把 `document = {**PLANNING_PROTOCOL_BINDING, "protocol_version": protocol_version}`
  改成 `document = {**PLANNING_PROTOCOL_BINDING}`（即漏掉请求里的协议名这一项）后：

```text
### M5 binding_hash computed over fewer items (protocol name dropped)
.................                                                        [100%]
17 passed in 0.42s
exit_status=0
```

- 该行为可分辨：变异后 `planning_protocol_binding_hash("planning-decision-v1")` 与
  `planning_protocol_binding_hash("legacy-plan-proposal-v1")` 返回同一个摘要（实测「unique digests across
  names: 1」），而对两个名字算出同一个绑定摘要与 `mission_planning_protocols.protocol_version` 一列
  在语义上是矛盾的。不是等价变异。
- 为什么现有测试杀不掉：唯一的摘要断言（`test_new_protocol_creation_writes_one_binding_with_frozen_hash`，
  测试文件第 205-209 行）把**期望值**写成 `{protocol_version: "planning-decision-v1", package_version: 4,
  prompt_version: "planner-hierarchical-v8"}` 的 sha256，而变异后的公式对该输入恰好算出同一个值
  （因为默认 `PLANNING_PROTOCOL_BINDING["protocol_version"]` 就是 `PLANNING_DECISION_V1`）。在裸
  `python` 下读 `planning_protocol_binding.py` **源码**按变异公式与按正确公式重算，两者都等于
  `0713d58c9fa27a8399621dd85677ac7b19852f6161b98ffe33ef4d2880d31979`，所以「没有断言」不是笔误而是
  这个断言构造方式的必然结果。
- 缺口有两处：
  1. 缺省协议名下 `planning_protocol_binding_hash(LEGACY_PLANNING_PROTOCOL)` 的正确值从未被任何用例钉住
     （该函数对缺省名给出 `dda73b2c...` 一类与「三项 sha256」不一致的值也全绿）；
  2. 全仓没有任何「摘要对协议名敏感」的断言。
- 建议补丁（两行即可）：

```python
def test_the_binding_hash_is_the_three_field_document_and_names_the_protocol(tmp_path) -> None:
    for protocol in (LEGACY_PLANNING_PROTOCOL, PLANNING_DECISION_V1):
        document = {"protocol_version": protocol, "package_version": 4,
                    "prompt_version": "planner-hierarchical-v8"}
        assert planning_protocol_binding_hash(protocol) == hashlib.sha256(
            json.dumps(document, separators=(",", ":"), sort_keys=True).encode()
        ).hexdigest()
    assert planning_protocol_binding_hash(LEGACY_PLANNING_PROTOCOL) != (
        planning_protocol_binding_hash(PLANNING_DECISION_V1)
    )
```

### P1-2 — 规定变异「把开关塞进 policy_snapshot」存活：`SNAPSHOT_FIELDS` 的白名单条目对不上任何配置字段（测试缺口）

- 位置：测试文件第 248-267 行（`test_policy_snapshot_digest_does_not_include_planning_protocol`）；
  对照实现 `src/agent_orchestrator/governance/policies.py:224`（`SNAPSHOT_FIELDS`）、
  `:374-377`（未分类即 `ValueError`）、`:392`（只把 `include` 的项写进 `config`）。
- 事实：在 `SNAPSHOT_FIELDS` 里加一行 `"planning_protocol_version": "include",` 后：

```text
### M9 policy snapshot carries the switch
17 passed in 0.42s
exit_status=0
```

- 该变异为什么可分辨（且是真实风险模式）：`SNAPSHOT_FIELDS` 的白名单是**按配置字段名**查的
  （`SNAPSHOT_FIELDS.get(name) == "include"`，`name` 来自 `OrchestratorConfig` 的 dataclass 字段）。
  一旦哪天为接线把开关做进配置（或把 `SNAPSHOT_FIELDS` 的 key 写成实际配置字段名，例如
  `"planning_protocol"`），这一行就会真的把开关写进 `policy_snapshot()["config"]`。实测：变异后
  `SNAPSHOT_FIELDS.get("planning_protocol_version") == "include"` 而 `config` 里仍没有这个键，
  摘要哈希也不变——也就是说这条断言**当前只能证明「这个不存在的键今天不会被写进去」**。
- 缺的是「按配置字段名注入」的那一格。建议补丁（不改白名单，先用一个假配置字段验证机制）：

```python
def test_the_snapshot_mechanism_itself_would_expose_a_config_field_marked_include(monkeypatch) -> None:
    # The guard above only names a field OrchestratorConfig does not have.  Pin the
    # mechanism: a field the config really carries, marked "include", reaches the digest.
    from agent_orchestrator.governance import policies

    witness = policies.SNAPSHOT_FIELDS.get("extra_sources")
    monkeypatch.setitem(policies.SNAPSHOT_FIELDS, "extra_sources", "include")
    try:
        snapshot = policies.policy_snapshot(OrchestratorConfig(evidence_root=tmp_path))
        assert "extra_sources" in snapshot["config"] or witness is not None
    finally:
        pass
    monkeypatch.undo()
    assert "planning_protocol_version" not in json.dumps(
        policies.policy_snapshot(OrchestratorConfig(evidence_root=tmp_path))
    )
```

（更省事的等价写法：把 `SNAPSHOT_FIELDS` 的 key 换成配置真有的字段名跑一次，断言摘要**会**变，
从而证明「摘要不含开关」这条断言不是空转。两种写法任选其一，要点是让该用例对着机制而不是对着一个
配置里不存在的键名断言。）

### 存活的四个：判定依据

- **N2 等价（只影响未知名，且不可达）**：`binding_document()` 的实参在全部生产调用路径上要么已被
  `checked_planning_protocol` 校验（`planning_protocol_replay_conflict` 先 `checked`），要么来自
  `MissionSpec.__post_init__`/`create_mission` 门卫（`bind_planning_protocol` 的入参）。
  实测：直接调 `binding_document("planning-decision-v99")` 在变异下会返回文档，但该函数**不是**
  本片对外承诺的入口，且没有任何 `src/` 调用方会传未校验的名字。属**防御性重复校验**被移除，不是行为缺口。
- **N4 等价（不可达）**：要让「无行」分支与请求的 wire 名不一致，必须构造出一个**规格文档与已存任务
  逐字节相同、但协议名不同**的请求。而 `to_json()` 会把新协议写进文档、缺省名被省略，所以协议名一变
  `spec_hash` 就变 → `create_mission` 在到这条检查之前先抛「different specification」（第 1 轮 §2.4 已实测）。
  实测本轮：legacy 任务上 `replay_conflict(...,"planning-decision-v1")` 在变异下返回 `None`，
  但没有任何合法输入能走到这里。**等价变异**，已备案。
- **N5 等价（不可达）**：该缓存的键是 `mission_id`，而 `Store.find_mission` 在事务内查库、任务 id 是
  `(tenant_id, idempotency_key)` 的确定性函数。「先记 miss、随后同一 store 里为同一 id 写入绑定行」
  只有通过公开 API 才能发生，而公开 API 里 `create_mission` 的绑定写入与 id 分配在同一事务内、
  读回之前不会让任何其他代码观察到；实测「两个库同名 mission」的场景在变异下仍答对（第二库有行，
  缓存里没有该项）。**等价变异**，已备案。
- **N10 真等价**：同一事务内交换两条语句的顺序，对提交后的状态、回滚语义、任何读路径都没有影响
  （实测：回滚后绑定 0 行、mission 不存在，与未变异一致）。**等价变异**。

### N7 / N9：可分辨但不在本片验收面

- **N7**（环境变量只给已存行改名）**行为可分辨**：置
  `SIMPLE_HARNESS_PLANNING_PROTOCOL=legacy-plan-proposal-v1` 后，
  `planning_protocol_for_mission()` 对已绑新协议的任务返回 `legacy-plan-proposal-v1`（实测输出见下），
  而现有用例 `test_the_durable_binding_ignores_the_ambient_environment` 把该变量**置成与新协议行
  相同的值**（`PLANNING_DECISION_V1`），因此观察不到「改名」。

```text
reader reports: legacy-plan-proposal-v1
(the test sets that variable to planning-decision-v1, i.e. the row's own value)
```

  这一格属**测试缺口的边缘**：该用例验证的是「环境不改变结论」，而 N7 改变的是「同一行被报成另一个名字」，
  要杀它需要断言读回值等于**行里存的**协议名（当前用例已断 `== PLANNING_DECISION_V1`，只是环境变量的取值
  恰好与行一致，所以变异对不上）。**改进建议（可选，非阻塞）**：把环境变量置成与行**不同**的值再断言，
  即把 `monkeypatch.setenv("SIMPLE_HARNESS_PLANNING_PROTOCOL", PLANNING_DECISION_V1)` 改成
  `LEGACY_PLANNING_PROTOCOL` 并保留原断言——一行改动即可让 N7 也被杀死。
  之所以不判 P1：N6b（真正「用环境决定协议」的强度）**已被杀死**，本片的核心命题（§8.2 不得猜模式）
  有有效守卫；N7 是同一命题的弱化形状。

- **N9**（写入时对任何 wire 都存新协议的摘要）**行为可分辨且值得记一笔**：这只是
  `bind_planning_protocol` 的**合法入参**（两个冻结名之一）；通过公开写入器给 legacy 名写行后，
  行的 `protocol_version='legacy-plan-proposal-v1'` 与 `binding_hash` 不再自洽：

```text
row.protocol_version : legacy-plan-proposal-v1
row.binding_hash     : 0713d58c9fa27a8399621dd85677ac7b19852f6161b98ffe33ef4d2880d31979
sha256(row document) : d0c73f7a42d2ef14c85f04f6d2416f45500f3c8cfc37f12f7d71834e2355f3f9
self-consistent      : False
```

  但「给 legacy 名写行」在**生产路径上不会发生**（`create_mission` 只在 `PLANNING_DECISION_V1` 时调用它，
  见 `commit_service.py:834`），所以这是**不可达**的可分辨变异——除非将来有调用方直接调该写入器。
  与 N7 同类：列为 **P3（非阻塞，建议后续接线片或 H1-I 的变异集收口时顺手钉住）**。
  一行可杀：「给 legacy 名写行后断言 `binding_hash == sha256(该行三项文档)`」。
