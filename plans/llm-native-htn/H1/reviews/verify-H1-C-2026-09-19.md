### P1-3 — `BlockError` 未知 reason 的兜底分支（`_BLOCK_ERROR_CODES.get(..., MALFORMED_DECISION)`）没有任何测试；把兜底码换掉全套仍绿
- 位置：`src/agent_orchestrator/planning/decision_codec.py:280-285`（`.get(..., MALFORMED_DECISION)` 兜底）。
- 事实：`extract_block`（H1-C 未改动）只可能抛 5 个 reason：`empty_output / block_missing / block_ambiguous / invalid_json / not_an_object`，且这 5 个**全部**在映射表里有明确行。因此兜底分支在当前调用路径上不可达；测试对它的唯一断言是「映射表末行是 `matches=None`」那类表结构断言，与这个 `BlockError` 兜底无关。
- 复现（把兜底码改成 `MULTIPLE_DECISIONS`，全套仍绿）：
  ```text
  $ PYTHONPATH=src uv run --offline pytest tests/orchestrator/full_target -q -p no:cacheprovider
  3189 passed, 2 skipped in 124.07s (0:02:04)
  $ PYTHONPATH=src uv run --offline pytest tests/orchestrator/full_target/test_planning_decision_codec.py -q -p no:cacheprovider
  42 passed in 0.25s
  ```
- 为何是 P1 而非 P2：C.1 的「BlockError 映射」是任务书逐条写死的三行映射，兜底码属于规格文本；它现在既无行为护栏、又不可达——属于「测试缺口」，须补一条直接注入未知 reason 的单元断言（或断言 reason 集合是闭集）以消除歧义。

### P2-1 — mixed 守卫是纯子串匹配，正文里的同名字面量会误报
- 位置：`src/agent_orchestrator/planning/decision_codec.py:232-238`（`f"<{tag}>" in text`）。
- 事实：只要文本任意位置出现 `<plan_revision_proposal>` 或 `<method_proposal>` 子串即判 `MIXED_PROTOCOL_BLOCKS`，即使该子串只是 `rationale` / `bindings` 里的引用文本：
  ```text
  rationale 含 "<plan_revision_proposal>"      -> MIXED_PROTOCOL_BLOCKS
  bindings  值含 "<method_proposal>"           -> MIXED_PROTOCOL_BLOCKS
  ```
- 说明：任务书 C.1 第 2 步原文就是「若文本还含 `<...>`（即使 extract_block 已成功）→ MIXED_PROTOCOL_BLOCKS」，且要求「不改 extract_block」。故这是**规格自带的过近似**，非实现偏离；即使任务书原文未加「同时出现（真块）」的限定。`</planning_decision>` 出现在字符串中会因非贪婪正则提前截断而报 `MULTIPLE_DECISIONS`/`MALFORMED_DECISION`，同属 `extract_block` 的既有行为（对任意 tag 都如此，已用 `widget` 交叉验证）。仅记录，不阻塞。

### P2-2 — 超长整数字面量会漏出裸 `ValueError`（非 `PlanningDecisionCodecError`）
- 位置：`src/agent_orchestrator/planning/decision_codec.py:280`（调用点）/ 真正来源 `src/agent_orchestrator/runtime/output_blocks.py:43`（`json.loads`，H1-C 未改动）。
- 复现：
  ```text
  $ PYTHONPATH=src uv run --offline python -c "...
  parse_planning_decision('<planning_decision>{"schema_version":' + '9'*5000 + '}</planning_decision>')"
  ValueError: Exceeds the limit (4300 digits) for integer string conversion: value has 5000 digits; use sys.set_int_max_str_digits() to increase the limit
  ```
- 边界界定：4300 位数字以内正常 `MALFORMED_DECISION`；4301 位起漏 `ValueError`。同一漏失在**未改动的** `extract_block` 与现网 `parse_plan_proposal` 上同样存在（已实测），因此**不是本片引入的回归**，而是 `extract_block` 的既有边界。任务书禁止改 `output_blocks.py`，故 C 片不应自行修；记录为后续片（或 `extract_block` 的独立小修）认领。

## 3. 七步流程顺序（双错输入：拒绝码稳定且与任务书一致）

脚本对每个双错输入各跑 200 次（确定性）：
```text
2 blocks + unknown key             -> MULTIPLE_DECISIONS     (step1 先于 step4)
2 blocks + bad system field        -> MULTIPLE_DECISIONS     (step1 先于 step6)
mixed + invalid JSON               -> MALFORMED_DECISION     (step1 先于 step2)
mixed + unknown key                -> MIXED_PROTOCOL_BLOCKS  (step2 先于 step4)
unknown key + system field         -> MODEL_SET_SYSTEM_FIELD (step6 先于 step4，journal 写死口径)
0 blocks + method block            -> DECISION_BLOCK_MISSING (step1)
legacy + method + 2 decision        -> MULTIPLE_DECISIONS    (step1)
invalid payload + system field     -> MODEL_SET_SYSTEM_FIELD (step6 先于 step5)
bad decision_type + system field   -> MODEL_SET_SYSTEM_FIELD (step6 先于 step5)
200 次重复：{'MIXED_PROTOCOL_BLOCKS': 200} / {'MULTIPLE_DECISIONS': 200}
```
判定：顺序与 C.1 的 1→7 一致；第 4 与第 6 步的相对次序（系统字段先判）是任务书未写死、由 journal-C §2.4「顺序即判码」显式记录的口径，实测稳定。C-N7 的「二选一必须稳定」口径满足（未知 Core 外键 → `UNKNOWN_FIELD`；键在系统字段集且出现在结构层 → `MODEL_SET_SYSTEM_FIELD`）。

## 4. 任务书之外的 8 个刁钻输入（自写，逐个记录）

命令：`PYTHONPATH=src uv run --offline python /tmp/h1c_adv.py`
```text
1 block nested same-name tag text in rationale -> PARSED
2 over-long rationale (4001 chars > 4000)    -> CodecError/MALFORMED_DECISION
3a BOM before the block                      -> PARSED
3b BOM inside the block                      -> CodecError/MALFORMED_DECISION
4 duplicate decision_type key                -> PARSED
5a system field as a payload structural key  -> CodecError/MODEL_SET_SYSTEM_FIELD
5b system field as another payload key       -> CodecError/MODEL_SET_SYSTEM_FIELD
6 system field inside reason_refs[0]         -> CodecError/MODEL_SET_SYSTEM_FIELD
7a bindings named scope/plan_revision/mission_id -> PARSED
7b bindings with a nested system-named key   -> PARSED
8 unicode-escaped key \u006dission_id        -> CodecError/MODEL_SET_SYSTEM_FIELD
```
逐条是否合理：
1. 块内 `rationale` 文本含同名字面量时的实测：单独的开标签 `<planning_decision>` → PARSED；含单独闭标签 `</planning_decision>` → `MALFORMED_DECISION`；含完整一对 `<planning_decision>x</planning_decision>` → `MALFORMED_DECISION`（`extract_block` 的不捕获正则把字符串里的第一个闭标签当成块尾，截断后 JSON 变成 `Unterminated string`）。成因是冻结的 `extract_block` 正则，对任意 tag 都如此（已用 `widget` 交叉验证，见 P2-1），受「不改 extract_block」约束不可在本片修。合理与否：建议 H1-E/F 在 prompt 里禁止模型在正文里书写标签字面量；本片记录不阻塞。
2. 4000 上限来自 V2 §16（补遗七.3「理由文字上限用 4000」），4001 → `MALFORMED_DECISION`，4000 → PARSED。合理。
3. 块**前**的 BOM 被 `extract_block` 容忍（BOM 在块外，散文允许）→ PARSED，合理；块**内** BOM 使 JSON 非法 → `MALFORMED_DECISION`，合理。
4. 键重复的 JSON：`json.loads` 末值胜出，`{...,"decision_type":"WAIT","decision_type":"REFINE",...}` → PARSED（取 REFINE）。这是 `json` 的标准行为、非本片可改；保守起见应视为可接受（模型不会故意重复键），但**没有**测试钉住该行为——记录为 P2 观察项（未列入 P1，因为 §14/§15 未规定重复键语义）。
5. payload 自身的键写系统字段 → `MODEL_SET_SYSTEM_FIELD`，合理（§32 结构层）。
6. `reason_refs[]` 条目里的系统字段 → `MODEL_SET_SYSTEM_FIELD`，合理。
7. `bindings` 里参数名叫 `scope`/`plan_revision`/`mission_id`/`decision_id`（含嵌套）→ PARSED，完全符合 §32「不扫描 arbitrary domain parameter map 的 key 名」与 C-N8。合理。
8. `\u006dission_id` 转义键名在 `json.loads` 后归一为 `mission_id` → `MODEL_SET_SYSTEM_FIELD`，正确（转义不构成绕过）。合理。

（另测：60/500 层深嵌套、1200 层 JSON、`NaN`/`Infinity`、坏 UTF-16 转义、非对象 `reason_refs`、300 层括号——全部稳定 `MALFORMED_DECISION`，无异常泄漏；唯一例外是 P2-2 的超长整数字面量。60000 次随机字节 fuzz 无任何异常类型逃逸。）

## 15. SURVIVED 的逐条定性

### 15.1 N1 / S6 —— 等价变异

{bogus, bogus2}     -> UNKNOWN_FIELD            （原版与变异版一致）

即该变异在当前合同层下**不可观测**（`ProposeMethodDecision.from_json` 要求 `method_proposal` 必填且是对象，`None`/缺失都到不了 codec 的内层校验）。判 **P2 观察项**：属实现层防御分支，而非可达缺口；若将来合同层放宽（例如允许 `method_proposal` 缺省），这条就会变成真缺口。

### 15.10 E1 —— 等价变异
`SYSTEM_FIELD_KEYS` 是 `frozenset`，成员集合不变时元素顺序无语义；新用例 `test_the_system_field_keys_are_exactly_section_32` 断言集合相等（非序列相等），故不杀。**等价变异**（规格要求的是键集，不是顺序）。
