### P1 必修

**P1-A：`$defs/blockedItem.detail` 的 Schema 类型与 codec 可空性不一致（Schema 漂移）**
- 位置：`src/agent_orchestrator/contracts/schemas/planning-decision-v1.schema.json:525-529`
  ```json
  "detail": { "type": "string", "minLength": 1, "maxLength": 20000 }
  ```
- 对照代码：`src/agent_orchestrator/contracts/planning_decisions.py:1232`（`detail: str | None`）、`:1237`（非 `OTHER` 可留 `None`）、`:1243`（`to_json` 恒发 `"detail": self.detail`，即 `null`）。
- 规制依据：V2 §28 明写 blocked 项 `{"code":…,"detail":"…"}`，仅 `BlockerCode.OTHER` 时 detail 必填（`H1-V2对照源码冲突检查` 载 “`BlockerCode.OTHER` 仅作封闭枚举的逃逸阀，detail 必填”）；非 `OTHER` 类型不得强制 detail。
- 复现（命令与尾行，见逐项 2(f)）：codec 接受 `{"code":"NO_USABLE_METHOD"}` 并回吐 `{"code":…,"detail":null}`；同一 `to_json` 输出被 Schema 拒绝 `$.payload.blockers[0].detail: type string != NoneType`。
- 影响：所有非 schema-engine 消费方（其它语言 Host、静态 schema conformance）会把一个 Python 权威编解码器认为**合法**的 decision 判为**非法**；这正是 V2 §14 要“其它语言 Host 与 fixtures 共用同一 wire 形状”的那条用途。
- 修复（不改 `planning_decisions.py`，符合本片零改动约束）：把 `:525-529` 的 `detail` 改为
  ```json
  "detail": { "type": ["string", "null"], "minLength": 1, "maxLength": 20000 }
  ```
  修后须保证 `test_every_declared_cap_equals_its_python_constant` 仍能定位 `blockedItem/properties/detail/maxLength`（`["string","null"]` 下 `maxLength` 仍在同一 `properties.detail` 节点，测试通过）。**已实测**该改法使 `json_schema` 用例仍 86 passed，且把“codec-canonical 输出被 Schema 拒绝”从 10 例降到 0 例。

**P1-B：测试缺口——没有“codec 合法输出必须被 Schema 接受”的用例（存活变异 M7b）**
- 位置：`tests/orchestrator/full_target/test_planning_decision_json_schema.py`（现有用例偏重“Schema vs Python 常量”的**单向**镜像；缺“codec → Schema”的**反向**接受性检查）。
- 复现：把 `blockedItem.detail` 设为 `{"type":"string",…}`（本片现状），跑本测试文件仍 86 passed；即该文件对 P1-A 这一类漂移**完全无感**。
- 修复建议（补 1 条用例，仍无需 `jsonschema` 依赖）：遍历全部 `valid/*.json` 与若干“codec 合法变体”（如非 `OTHER` 且省略 `detail`），断言“`to_json()` 的输出满足 Schema 的**类型/可空性**约束”。可用最小自检脚本（本报告所用的 `mini_jsonschema` 子集）或直接断言“Schema 的 `type` 集合 == codec 注解的类型集合”的方式实现。
