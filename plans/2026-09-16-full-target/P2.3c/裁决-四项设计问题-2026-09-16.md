## 裁决 1 —— `validity_witnesses` 唯一索引

### 裁决（一句话）

**改索引，不合并两条许可链**：走新迁移 18，给 `validity_witnesses` 增加一列
`subject_digest`（"这份许可是为哪个被许可对象签发的"），把唯一索引换成
`(mission_id, consumer_kind, consumer_id, purpose, subject_digest, scope_id, scope_epoch, support_revision)`；
`subject_digest` 由签发方**显式声明**（DATA 链 = `acceptance:<acceptance_id>`，
前置条件链 = `conditions:<所有 condition digest 排序后的 sha256>`），不是从行里猜出来的。

### 规范依据

1. AER §8.1 对象表（`design.zh-CN.md` L300）：
   > ValidityWitness | consumer、purpose、as_of、**support_selection**、read-set、scope epochs、not_after、阻断理由 | 本次是否可以使用，不是永久授权令牌

   一条许可的身份里本来就含 `support_selection`——"这次用的是哪一份支持"。
   两份不同的 support selection 是**两条许可**，把它们压成一行等于删掉规范要求保存的那一维。

2. AER §18 存储表（`design.zh-CN.md` L635）：
   > validity_witnesses | `(consumer_ref,purpose,scope)`、支持 revision/epoch、as_of/not_after

   规范只钉了"按 consumer/purpose/scope 索引"，**没有**规定"一个 consumer 一个 purpose 只能有一行"。
   现仓库把它实现成 UNIQUE 是一次收紧，收过头了。

3. AER §8.2「四个维度，禁止挤成一个 VERIFIED 字段」：
   > 1. 证据结论 …… 4. 使用权与可用性 …… UI 可显示受控的综合状态，但内部保持四个维度。

   同理反向成立：把"某份输入被撤销"与"某个前提变 UNKNOWN"压成同一个 `BLOCKED`，
   就是把多个维度挤成一个字段，只是挤的是坏消息那一侧。

4. TG 设计稿 §9：
   > 每个前提的支持见证与检查点均保存。

   合并后只剩一个 `support_revision` 与一组 `support_refs`，"每个前提的检查点"不再可分辨。

5. AER §10.3「不过度重跑」：`UNCHANGED` 不创建新工作。合并链只能带一个 `support_revision`，
   任何一条新观察都会让**全部** DATA 许可一起失效并重签，正是这节禁止的全量重算。

6. 硬约束（决定"不能加契约字段"）：`contracts/evidence_state.py:566` 的 docstring 写明
   "Field names and enums follow `annex/aer-1.0/schemas/validity-witness.schema.json` exactly"，
   而该 schema 顶层 `"additionalProperties": false`（schema 文件 L204），`purpose` 是封闭 enum。
   因此**不得**给 `ValidityWitness` 加 `subject_ref` 字段，也**不得**新增 purpose 值。
   `subject_digest` 只能是**存储层派生列**——它不进 `witness_json`，契约字节逐字不变。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| A. 合并成"这个消费者此刻可以开始"一条许可（truth 取 AND） | 违反上引 1/3/5：`support_selection` 不可分、每条前提的检查点丢失、一次观察触发全量重签。更致命的是**增量签发**：DATA 许可是随着生产者陆续验收一条条签的，合并后每多一条验收就要换一个新的行身份（内容哈希变），"最新那条"的择取变成组合爆炸。 |
| B. 新增 purpose 值（如 `START_DATA`） | schema 的 purpose 是封闭 enum 且 `additionalProperties:false`；DB CHECK 也钉死七值。且规范里 purpose 是**用途/阶段**（§6.6 SELECT/START/MAINTAIN/ACCEPT、AER §10.4），两条链的用途确实都是 START，改 purpose 是拿阶段字段冒充对象字段。 |
| C. 用 `scope_id` 区分两条链 | `scope_id` 的语义是 epoch 分区（AER §10.2「epoch 可先使用 Mission scope……后来按 scope 分区也须保持同一合同」）。拿它区分对象会让两条链各有独立 epoch，一次撤销不再同时打断两条链，直接破坏 §10.2 的同步安全屏障。 |
| D. 维持 2c 的"先到先得 + 记 `HierarchicalWitnessKeyTaken`" | 诚实但不可用：`leaf_acceptance._outputs` 用 `len(list_observations(mission))` 当 DATA 的 support_revision，`issue_start_witnesses` 用 `snapshot.support_revision`（同样是观察条数），两者**系统性相等**，所以"带前提的方法 + 有 DATA 边的叶子"必然撞键，不是偶发。 |

2. **新建** `src/agent_orchestrator/knowledge/validity.py`（§18.1 已给这个文件名留了位置）：

4. `orchestrator/hierarchical_dispatch.py`：
   - `issue_input_witnesses`：`self._record_witness(mission_id, witness, subject=f"acceptance:{output.acceptance_id}")`。
   - `issue_start_witnesses`：`subject=f"conditions:{sha256_hex_text('|'.join(sorted(by_digest)))}"`。
   - `_record_witness` 增 `subject` 形参并原样透传。
   - **`_witness_key_taken` 与常量 `WITNESS_KEY_TAKEN` 保留不删**：它现在只在"同一 subject 下两个不同结论"时触发，
     那是真异常（同一次世界读数得出两个答案），仍应记录而不是吞掉。docstring 改写说明这一点。
   - `leaf_acceptance.py::_witness`（ACCEPT 见证）的 `insert_validity_witness` 调用同步补 `subject=f"acceptance:{acceptance_id}"`。

5. 事件：**不新增事件类型**。`HierarchicalWitnessKeyTaken` 语义收窄（payload 增 `subject_digest` 字段）。

## 裁决 2 —— 层次 Mission 空转要不要停成 FAILED

### 裁决（一句话）

**要停，但不是第一次空转就停**：在**同一次 `run()` 内**再做一遍完整确认轮（重签见证、重跑取证轮、
重读 admissions），若"世界指纹"与第一遍逐字相同，则由 orchestrator 循环调用
`CommitService.fail_mission`，Mission → `FAILED`，`stop_reason` 用**新值**
`MissionStopReason.NO_DISPATCHABLE_WORK = "no_dispatchable_work"`，
`final_report` 里按 §6.4 的 `BOUND_REACHED` 体例列出全部 withheld occurrence、detail codes 与未决义务；
`HierarchicalMissionStalled` 保留原样（仍是非判决的记录），停机是它之后的第二步。

### 规范依据

1. §9.1 ExecutionFeedback 决策表（诊断 → 计划动作）：
   > 重复无进展 | Failure Analyst、换策略或停止；计数不因换名重置

   "停止"是规范给出的合法终点；"计数不因换名重置"要求停机依据必须是**同一身份下的重复**，
   所以必须先有"确认不变"这一步，不能一见空转就停。

2. §15：
   > 引入 `Commitment` 表示长期个人责任，`ExecutionCycle` 引用一次有限 Mission。

   Mission 是**有限周期**。"外面补一个 demand 就能继续"不是不停机的理由——那属于下一个周期／Commitment，
   不属于本周期。本周期必须终结。

3. §6.4：
   > 燃料耗尽的终态是 `BOUND_REACHED`，报告已展开结构和未决义务，不是 `UNSOLVABLE`。

   终态的**形状**由此钉死：停机报告必须列出已展开结构与未决义务，不得宣称目标不可能。

4. §7.4：
   > 求解器 `UNSOLVABLE` 只在对应问题/模型/求解模式确实支持该结论时使用；超时、预算结束、模型不完整分别返回，不能共同解释成现实目标不可能。

   TG 设计稿 §8.2 同义：
   > 输入缺失、观察服务不可用、外部操作 UNKNOWN 是不同原因，不统一转换为"任务失败"。

   → 因此**必须新增 stop_reason**，不得复用既有值把三件事压成一件。

5. §18.5 硬约束 4 的同一条原则（"新模式不重定义旧语义"）：
   legacy `NO_PROGRESS` 是 **Task 级**、由 `_enforce_no_progress` 按 `no_progress_count(task.id)`
   判定并调 `stop_task`（`event_handler.py:4789-4800`）。拿它做 Mission 级空转会静默重定义旧语义。

6. §21.5 硬性不变量：
   > 缺根要求时根 Resolution 形成次数为 0；**「错误宣布完成」= 0**

   停成 FAILED 永远不会置 COMPLETED，也不经过根 Resolution，故该不变量**结构上不可能被本裁决破坏**。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| A. 永远只记录、不停机（2c 现状） | Mission 永远 `ACTIVE`，§15 的"有限周期"落空；§21.5 的配对评测要求每局结束，不结束的局无法进入 McNemar 口径。 |
| B. 第一次空转就 FAILED | 违反 §9.1 的"重复无进展"限定；一次取证轮/一次见证重签就可能把局面推动（2c 冒烟第 6、7 轮就是这样），一次就停会扔掉真能跑的工作。 |
| C. 复用 `NO_PROGRESS` | 见依据 5：Task 级、attempt 计数语义，复用即重定义。 |
| D. 复用 `PLANNING_FAILED` | 语义是"规划没产出计划"。这里计划已提交、已派发、已有 Acceptance 落库，说 planning_failed 是谎报。 |
| E. 复用 `INSUFFICIENT_EVIDENCE` / `MISSION_CRITERIA_UNMET` | 这两个是**判决结论**。没有根 Resolution 就断言判据未达，等于 AER I05「审阅结束 ≠ 通过」反向违规（凭空造一个判决）。 |
| F. 新增 `MissionStatus.PAUSED` | §15 明写"**为了保留现有 Mission 终态**"才引入 Commitment/ExecutionCycle；加状态会改 §25.1 状态机与全部 legacy 转移表，代价与风险都远超收益。 |

### 落地改法

1. `contracts/state_machines.py::MissionStopReason` 新增：
   ```python
   NO_DISPATCHABLE_WORK = "no_dispatchable_work"  # P2.3c 2c: 层次计划在本周期内无可派发工作
   ```
   （只加枚举值，不动任何既有值的字面量。）

2. `orchestrator/event_handler.py`：
   - `_record_hierarchical_stall` **保持现有行为不变**（记录、不判决），但在 payload 里追加
     `"fingerprint": <str>`，由新私有函数 `_stall_fingerprint(mission, admissions, rows)` 计算：
     `sha256(canonical_json({plan_revision, sorted 拒绝 (occurrence, reason, detail_codes),
     sorted admitted_not_dispatched, sorted unfinished task ids,
     scope_epochs, support_revision=len(list_observations), sorted 已 admit demand 的 obligation ids}))`。
   - **新增** `async def _confirm_and_stop_stalled(self) -> None`：在 `run()` 的空闲返回路径上，
     `_record_hierarchical_stall()` 之后调用。它对每个刚记过 stall 的 Mission：
     再跑**恰好一轮**完整确认（`issue_start_witnesses` → `issue_input_witnesses` →
     `run_evidence_round` → `advance_compound_phases` → `admissions`），重算指纹；
     指纹变了 → 什么都不做（让循环继续，下一轮自然往前走）；
     指纹逐字相同 → `self.commit.fail_mission(mission.id, stop_reason=MissionStopReason.NO_DISPATCHABLE_WORK, detail={...})`。
     **必须硬编码"只多跑一轮"**，不得循环重试，否则空转变成忙等。
   - `detail` 内容（§6.4 形状）：`plan_revision`、`withheld`（全部，不采样）、`admitted_not_dispatched`、
     `outstanding_obligations`（lifecycle 仍 `UNSATISFIED` 的 obligation id + goal_signature id）、
     `fingerprint`、`confirmed_after_one_more_cycle: true`。
   - `_new_mode(mission)` 接线点 11 → 12；`test_the_event_handler_asks_the_mode_before_consulting_the_assembly`
     的计数同步改并写理由。

3. 事件：`fail_mission` 已经发 `MissionFailed`，**不新增事件类型**。
   `HierarchicalMissionStalled` 仍然先于它出现，两条连起来就是完整叙事
   （"卡在哪" → "又确认了一遍还是卡在这" → "本周期终止"）。

4. 迁移：**无**。

### 对 §21.5 硬性不变量与旧模式零回归的影响

- **「错误宣布完成 = 0」**：结构上不可能被破坏（FAILED 路径不经过根 Resolution，也不置 COMPLETED）。
- **缺根要求时根 Resolution 形成次数为 0**：不触及。
- **预算守恒**：`fail_mission` 内部已 `_cascade_stop`（取消 READY/ACTIVE Task、关闭 dispatch intent、释放预留），
  守恒等式在局末仍成立；测试 5 里顺带断言 `conservation()` 等式。
- **旧模式零回归**：新增枚举值不改任何既有字面量；新分支被 `_new_mode is None` 挡在 legacy 之外；
  `MissionFailed` 事件的 payload 形状不变（只是 `stop_reason` 取了新值）。
- **对 H 臂成绩的影响（须在验收报告里写明）**：原本停在 `ACTIVE` 的局现在会记为 `FAILED`。
  官方评分本来就按最终产出判，空转局本来就是失败局，所以**通过率口径不变**；
  变的是"局能不能结束"，而配对协议要求每局结束。这不是把成绩做差，是把无法收口的局收口。

## 裁决 3 —— 生产侧没有任何路径 `admit_demand`

### 裁决（一句话）

**「要这份工作的人」= 采用该方法实例的那个父义务的 slot**（`DemandRef(consumer_instance, slot, obligation, producer, state)`），
demand 在 **`commit_plan_revision` 的同一个事务里**、由**该命令的 principal**（`authorize_command_identity` 已认过的那个）
显式 admit——这是规范明文支持的，不是静默代办；
根责任的 demand 仍由注册它的调用方 admit，但必须走**同一个**带 principal 的生产入口
`ObligationCommitsMixin.admit_obligation_demand(...)`，不再只存在于冒烟装配里。

### 规范依据

1. TG 实现稿 §7.3 `commit_plan_revision` 伪码（L317）明文列了这一步：
   > `validate_data_bindings_and_demand(delta, current)`

   demand 的校验/建立**本来就在这个事务里**，不是外挂。

2. TG 实现稿 §3.2（L112）：
   > 替代方法不自动获得执行资格；搜索可保留多个候选，**只为当前批准的探索/执行范围创建真实 demand**。

   "当前批准的执行范围"＝这次 PlanRevision 采用（adopt）的方法实例。采用即批准，采用的那一刻就是 admit 的时刻。

3. TG 实现稿 §9.2（L395）给出 demand 的身份形状：
   > 真正共用仍在执行的 Task 时增加 `DemandRef(consumer_instance, slot, obligation, producer, state)`。

   四个字段里 `consumer_instance` + `slot` 就是"谁在要"。因此 requester 不是 Mission 根，也不是模型。

4. §6.1：
   > 语义上确实新增的责任由**显式命令**创建，并记录与父责任的关系。

   `ObligationOpening` 已有 `relation`（`REFINES_PARENT` / `INDEPENDENT_AUTHORIZED`）与 `authorization_ref`；
   `opened_by: Provenance` 由系统填（`contracts/htn.py:2782`「a model may propose the shape of the work,
   never the fact that a new responsibility was authorised」）。这三者合起来就是规范要求的"显式授权记录"。

5. §24.1 裁决 9：
   > 四种去重分开（幂等重放 / slot 重复 / 相似候选 / 共享执行）；**活跃共享用 DemandRef**；退出分支只删自身采用关系。

   → 退出（RetireMethodUse）时必须对称地 `withdraw_demand`，只删自身那条。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| A. Mission 根是 requester | 与 TG §9.2 的 `DemandRef(consumer_instance, slot, …)` 直接矛盾；且"退出分支只删自身采用关系"将无法表达——根不是分支。 |
| B. 由部署在 commit 之外补 admit | 会出现"计划已提交、occurrence 已物化、demand 还没到"的中间态；§9.4 要求原子切换"不允许一半新图、一半旧图继续派发"。 |
| C. 由模型在提案里声明 demand | §18.5「Mission 身份、账户、实际 scope 和 execution generation 由系统绑定」、`opened_by` 由系统填。模型自报授权即伪造准入。 |
| D. 干脆把 `has_admitted_demand` 闸门从 readiness 去掉 | 那是 §24.1 裁决 9 与 TG 实现稿 §6「允许派发的必要条件：……**当前有获准 demand**」直接要求的闸门，不能拆。 |

### 落地改法

1. `contracts/obligations.py` / `storage/obligation_store.py`：`admit_demand` 签名不变（已具备）。

2. `planning/htn/compiler.py::apply_obligation_openings`：在 `ledger.open_from(...)` 之后，
   对每条 opening 按下列**确定性规则**决定是否 admit（规则写进 docstring）：

   - `relation is REFINES_PARENT`：
     - 必须能在同一 `delta` 的 `child_bindings` 里找到**恰好一条** `binding.obligation_id == opening.obligation_id`，
       由它给出 `(instance_id, slot_key, occurrence_id)`；找不到 → `ContractError("没有任何被采用的 slot 在要这份工作")`，整条 commit 拒绝。
     - 父账户必须 `has_admitted_demand` 为真；否则 → `ContractError`（不能细化一个没人要的义务）。
     - 满足则 `ledger.admit_demand(opening.obligation_id)`。
   - `relation is INDEPENDENT_AUTHORIZED`：
     - 必须 `opening.authorization_ref is not None`；否则 → `ContractError("独立责任需要自己的授权引用")`。
     - 满足则 admit，requester 记为该 `authorization_ref`（不继承父的 demand）。

   **不做任何默认放行**：两条分支之外一律不 admit 且拒绝 commit，而不是"开了但没人要"。

3. `orchestrator/plan_commits.py`：
   - `_check_budget`（事务外 dry-run，L796-800）与真正 apply（L916-919）都调同一个
     `apply_obligation_openings`，规则天然一致，不需要第二份实现。
   - 真 apply 分支里，每条 opening 追加一条事件（见 4）。回执 payload 的
     `"opened_obligations"` 旁增 `"admitted_demands"`。

4. `orchestrator/obligation_commits.py::ObligationCommitsMixin` 新增**唯一的**生产入口：

   ```python
   def admit_obligation_demand(self, mission_id, obligation_id, *, principal,
                               requester, evidence) -> ObligationAccountView
   ```
   - `requester`：`{"kind": "method_slot"|"authorization"|"mission_root",
      "method_instance_id": …, "slot_key": …, "occurrence_id": …, "authorization_ref": …}`
   - `evidence`：`REFINES_PARENT` → 父 obligation id + 采用它的 plan_revision；
     `INDEPENDENT_AUTHORIZED` → `authorization_ref`；
     `mission_root` → Mission 的 `requirement_refs`。
   - 发新事件 **`ObligationDemandAdmitted`**（payload：`obligation_id` / `parent_obligation_id` /
     `relation` / `requester` / `evidence` / `principal` / `plan_revision`），
     key = `f"{mission_id}:{obligation_id}"`（幂等）。
   - 对称的 `withdraw_obligation_demand(...)` 发 **`ObligationDemandWithdrawn`**，
     由 `resolution_commits` 的现有 `withdraw_demand` 与 RetireMethodUse 两处调用（§24.1 裁决 9「退出分支只删自身采用关系」）。

5. **根责任**：hierarchical Mission 的引导路径（当前只有冒烟装配和 `htn_world` fixture 在做）
   必须改调 `admit_obligation_demand(..., requester={"kind": "mission_root"}, principal=<创建 Mission 的 principal>,
   evidence=Mission.requirement_refs)`。裸调 `ObligationStore.admit_demand` 在生产源码树里应被静态守卫禁止
   （只允许 `obligation_commits.py` 与 `obligation_store.py` 自身出现该调用）。

6. 迁移：**无**（`demand_admitted` 列已存在，`ObligationStore.persist` 已经落它）。

### 必需测试

### 对 §21.5 硬性不变量与旧模式零回归的影响

- **预算守恒**：`open_from` 已把 fuel 从父账户划走，admit 只翻 `demand_admitted` 布尔位，不动额度；
  守恒等式不变。回归测试沿用 2c 的 `two_rounds` 夹具再跑一遍。
- **分解见证独立校验**：admit 让子 occurrence 真正可派发，见证从"计划上的" 变成"执行过的"，方向是补强。
- **「错误宣布完成 = 0」**：不触及完成判定。
- **缺根要求时根 Resolution = 0**：不触及。
- **旧模式零回归**：`obligations` 表与 `commit_plan_revision` 都是新模式路径；
  legacy Mission 不过 `plan_commits`。两个新事件类型只在 hierarchical 分支出现，
  旧事件 canonical JSON 字节不变（§18.5 硬约束 3）。
- **注意（实施者必看）**：本裁决会让**现有测试里那些"开了子责任但没 admit 也照常通过"的用例**变红。
  这是预期的——它们记录的正是这个缺陷。逐条改成显式 admit，不要靠放宽新规则让它们复绿。

## 裁决 4 —— 叶子产物 ↔ 输出端口配对规则

### 裁决（一句话）

**配对只依据 Worker 输出块里显式的 `outputs` 声明（端口名 → 该 Attempt 真实写过的一个产物路径），
端口名与 schema 由系统从方法契约/`DataRequirement` 给出并在验收时严格校验；
删除全部"按名字猜"与"一对一就配"的回退；未被任何端口认领的多余产物保留为证据产物、不进索引、不报错；
而一个 `required=True` 且**确有 DataRequirement 消费**的输出端口没有被认领时，在 `accept_review` 阶段
**结构化拒绝验收**（新 reason 码 `OUTPUT_PORT_UNCLAIMED`），不保守留空。**

### 规范依据

1. TG 设计稿 §3.2（L76）——这是本裁决的核心授权：
   > **模型只提供局部 key、业务目标与参数；Mission 身份、账户、实际 scope 和 execution generation 由系统绑定。**

   "哪个文件是 `repository_facts`"正是**局部 key**，只有写文件的那个 Worker 知道；
   而 `acceptance_id` / `content_hash` / `schema_ref` / `producer_result_id` / `support_revision` / `occurrence`
   全是系统绑定字段，模型一个都不填。现有 `check_against_ports` 已经守住了后半段。

2. TG 实现稿 §4.3（L182）：
   > 只有产物 schema、来源权限、输入版本与验收满足合同，才允许绑定。……
   > 无法证明兼容时**产生显式转换 Task 或拒绝**，不用 `Any` 放过。

   → 配不上时的正解是"拒绝"，不是"留空等着"。

3. TG 设计稿 §10.2（L299）：
   > 两个不同 hash 要映射到同一个最终 `report.md`，必须明确选择/转换/综合……
   > **不能用"B 拓扑更靠后"挑一个**，也不能为了获得覆盖许可临时加 ORDER 边。

   现行 `_port_for` 的两条回退（端口名是路径子串、一端口一产物就配）都属于"按位置/名字猜"，
   与这条同源禁止；`accepted_outputs.py` 自己的 docstring 也写了「It does not derive the port」——
   `accepted_outputs_for` 违反了同模块的既定约定。

4. §24.1 裁决 3：
   > DATA 走显式端口：DataRequirement（约定）→ 派发前 BoundInput → 不可变 InputManifest；
   > 单值端口唯一 binding、集合端口有序；**schema 精确匹配或注册兼容声明**。

5. §21.5 硬性不变量「错误宣布完成 = 0」：
   "绑错 artifact" 会让下游消费一份不是它要的数据并一路通过验收——这正是该不变量要消灭的失败模式。
   因此**宁可拒绝，不可猜**；但"猜"与"留空"之外还有第三条路：让模型说出来。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| A. 维持"名字匹配 + 一对一回退"（2c 现状） | 见依据 3：是 §10.2 禁止的按名/按位置猜。真实模型交 2 个文件、1 个端口、名字不符，直接静默停摆——2c 冒烟第 9 轮的卡点。 |
| B. 只靠方法契约的端口 schema 校验、由系统自动挑一个匹配 schema 的产物 | schema 通常只说"一个 JSON/markdown 文件"，匹配不唯一；自动挑就是回到按位置猜。 |
| C. 配不上就保守留空（现状语义） | 违反依据 2「无法证明兼容时……拒绝」；且留空的后果是 Mission 永远 `WAITING_DATA`，运维只能靠裁决 2 的停机收场，等于用一个缺陷掩盖另一个。 |
| D. 让模型自己写 `acceptance_id` / `schema_ref` / `content_hash` | 直接违反依据 1 与 §18.5「注册状态及准入回执由系统填写，模型不能自填 ADMITTED」的同一条原则。**明确禁止**。 |
| E. 多余产物一律拒绝验收 | 过严：调试脚本、日志、中间文件是正常产出；§10.2 只禁止"同一路径两个 hash 不作选择"，没禁止存在未声明产物。多余产物进 artifact 表作证据，不进 `acceptance_outputs`，即是诚实。 |

### 落地改法（含"最小改动、且不让模型自填系统绑定字段"）

1. **角色模板（最小改动）** `runtime/role_templates.py`：
   - 新增 `WORKER_HIERARCHICAL_VERSION = "worker-hierarchical-v1"` 与
     `HIERARCHICAL_WORKER_VERSIONS`，用 `_revise(WORKER, …)` 派生；
     `worker-v3` 与 `WORKER_V2` **字节一字不动**（冻结摘要测试原样通过）。
   - 只在 `result_envelope` 的字段说明里**加一行**：
     ```
     "outputs": {"<系统在输入 declared_output_ports 里给你的端口名>": "<你写过的一个文件路径>"}
     ```
     并写死三句话：端口名只能抄输入里给的，不能自己造；路径必须是你本次真实写过的文件；
     其余字段（版本、hash、验收 id）由系统填，不要写。
   - 选模板走 2b 已建立的**模式选提示词**机制（`_hierarchical_planner_template` 同形），
     部署 pin 只能在 hierarchical 版本之间选。

2. **给模型端口名（系统侧）**：hierarchical 叶子的 dispatch intent typed context 增
   `declared_output_ports: [{"port": …, "required": bool, "cardinality": …, "schema": {"id":…, "version":…}}]`，
   来源是 `TaskSemanticBindingV1.output_ports` 与该 revision 的 `DataRequirement`（取交集，以边为准）。
   由 `HierarchicalDispatch` 提供 `declared_output_ports_for(mission_id, task_id)`，
   复用 `accepted_outputs.declared_ports_in_revision`（不建第二份规则）。

3. **解析与校验** `runtime/output_blocks.py` + 结果 codec：
   - `outputs` 解析成 `tuple[PortClaim]`（`port_key`, `path`），**只解析这两项**。
   - 结构性拒绝（走现有 `BlockError` 有界修复，不另开请求，§18.5 C8）：
     端口名不在 `declared_output_ports` 里；同一端口被声明两次而该端口 `cardinality=SINGLE`；
     路径不在本次 Attempt 的产物列表里；`outputs` 里出现除这两项以外的键。

4. **配对** `orchestrator/leaf_acceptance.py::accepted_outputs_for`：
   - 签名增 `claims: Sequence[PortClaim]`；
   - **删除** `_port_for` 与它的两条回退，整函数改为：按 claim 取 port，
     用 `ResourceIdentity(namespace, normalized-path)`（§24.1 裁决 4）在 artifacts 里定位那一个产物；
     `schema_ref` **仍然取自 `DataRequirement`**（现状已对，不改）；
   - docstring 重写：规则是"声明的"，不是"猜的"。
   - `LeafAcceptanceAssembly.accept(...)` 增 `port_claims=` 形参；
     `event_handler._accept_hierarchical_leaf` 从 `stored.envelope.outputs` 取，与
     `self.store.list_artifacts(attempt.id)` 一起传下去。

5. **未认领端口的结构化拒绝** `orchestrator/resolution_commits.py::accept_review`：
   在现有四个 reason 码（`NO_PLAN_REVISION` / `OCCURRENCE_UNKNOWN` / `OUTPUT_NOT_DECLARED` / `OUTPUT_CONFLICT`）
   之外新增 **`OUTPUT_PORT_UNCLAIMED`**：事务内读该 occurrence 在活跃 revision 下
   `required=True` 且**确有 DataRequirement 消费**的输出端口集合，减去 `command.outputs` 覆盖的端口，
   非空即拒绝，payload 列出缺哪些端口与本次交了哪些产物。
   `outputs` 已进 `intent_hash`（2b §7 第 1 条），重放语义不变。
   拒绝**不撤销验证结论**（沿用 2b 既定："a refusal is recorded and does not undo the verification"），
   它进入 §9.1 决策表的"内容缺陷 → 原义务的新内容尝试"分支，由现有重试路径再交一次。
   —— 只有在这样的重试也用尽后，才落到裁决 2 的停机，两条裁决在此衔接。

6. 事件：**不新增事件类型**；`AcceptReviewRefused`（现有）多一个 reason 码。
   迁移：**无**（`acceptance_outputs` 表是迁移 17 的，形状不变）。

   `accepted_outputs_for`，并让 claim 为空；测试 1 与测试 4 必须变红

### 对 §21.5 硬性不变量与旧模式零回归的影响

- **「错误宣布完成 = 0」**：正面强化。删掉"一端口一产物就配"是删掉一条会把错产物喂给下游、
  并让下游一路验收通过的路径；`OUTPUT_PORT_UNCLAIMED` 则把"输出没交齐"变成显式拒绝而不是静默完成。
- **机制触发（共享子目标复用 ≥1 次）**：共享子目标的复用依赖 `acceptance_outputs` 真的有行；
  本裁决是让它真的有行的前提，对 §21.5 的机制触发门槛是必要条件。
- **分解见证独立校验**：端口↔产物从"推断"变成"声明 + 校验"，见证可独立复核，方向是补强。
- **旧模式零回归**：`worker-v3` / `WORKER_V2` 字节不变，legacy 冻结摘要测试原样通过；
  `result_envelope` 的 legacy 解析路径不变（`outputs` 是新模板才出现的可选字段，
  legacy 模板不提它、legacy codec 不读它）；`acceptance_outputs` 只有 hierarchical 分支写。
- **对真实模型的风险（须在验收报告写明）**：小模型可能漏写 `outputs`。
  这时表现是**显式拒绝 + 有界修复重试**（可观测、可计数），而不是 2c 那种静默 `WAITING_DATA`。
  §21.5 的报告里应把 `OUTPUT_PORT_UNCLAIMED` 的发生次数作为信息项记下来。
