## 结论

**修后可合。** 发现 **1 条 P0、2 条 P1**（均在「换方法」路径的边界上，主线「REJECT → 修复轮包有库 → retire+refine / 声明无方法→带 findings 合成 → 新 revision → ACCEPT」本身核对无误），另 7 条 P2。P0/P1 未代修。

- **P0-1** 重新采用一个曾被退（RETIRED）的方法实例——同一 occurrence + 同一方法 + 同一参数的 `instance_identity` 是确定性 id——`insert_method_instance` 撞 UNIQUE 约束，`StoreConflict` 从 `_cycle` 逃逸（`_cycle` 只宽恕 StoreBusy/CommitRejected/IllegalTransition），`run()` 崩溃，Mission 永远 ACTIVE、无 MissionFailed。默认配置下两次拒绝即可到达（见 P1-1），也可由修复轮 Planner 直接重提被拒方法到达（提示词只说「不要」，代码不拦）。
- **P1-1** 「有界」不成立：修复轮按 **plan revision** 计（每个替换 revision 又得到 1 次修复），被拒记录只认当前 revision 上仍 ADOPTED 的实例，旧被拒方法在下一 revision 重回候选、不再打 `rejected_by_root_review`。两方法库下 Planner 会 outer↔alt 振荡，直到结构预算 / token 池（P2.3j 顺手修让被退叶子不再占池）或撞上 P0-1。CHANGELOG 第 57 行「默认 max_root_review_repairs=1 下走不到」与实测矛盾（我实测 repairs=[1, 2]）。
- **P1-2** `retire_method`+`refine` 对**任何**已细化 occurrence 的 ADOPTED 实例都放行（不限于根评审拒绝的实例），系统无条件盖 `REQUEST_STOP_THEN_RECONCILE`，但没有任何东西去 stop / reconcile：被退叶子的 RUNNING attempt 仍 RUNNING、Task 行仍 READY、预留仍在，`mark_dirty(dispatch_generation_revoked)` 无人消费。P2.3j 目标场景（根评审前所有叶子已 COMPLETED）里无害，但编译侧没有把口子限在那个场景。

## 二、重点缺陷（P0 / P1，含复现与建议修法）

### P0-1 重新采用曾被退的方法实例 → `StoreConflict` 逃逸，`run()` 崩溃，Mission 永远 ACTIVE

- 位置：
  - `src/agent_orchestrator/planning/htn/grounding.py` L101–L118 `instance_identity`：id = hash(goal_id, occurrence, method_id, version, content_hash, parameters_digest)，「Same inputs, same instance」
  - `src/agent_orchestrator/orchestrator/plan_commits.py` L1101 `semantics.insert_method_instance(..., state="ADOPTED")`：RETIRED 行「不删除」（测试 `test_retire_and_refine…` 断言 `old in states RETIRED`），同 id 再插即 UNIQUE 冲突 → `StoreConflict`（`htn_store.py` L2340–L2342）
  - `src/agent_orchestrator/orchestrator/hierarchical_dispatch.py` L3440–L3560 `compile_proposal` / L3400–L3438 `apply_planner_reply`：只接 `PlanCommitRejected`；不检查新 draft 的 id 是否已存在、不检查 refine 的方法是否就是被退的方法
  - `src/agent_orchestrator/orchestrator/event_handler.py` L2012–L2028 `_cycle`：只宽恕 `StoreBusy` / `CommitRejected` / `IllegalTransition`；L4375–L4420 `_collect_plan_hierarchical` 只接 `GraphIntegrityError` / `NoApplicableMethodDeclared` / `ContractError`…，`StoreConflict`（StoreError）直接上抛
- 复现 1（直接）：`_seeded(alt=False)` 后 `world.plan(_replacement(world, world.contract /*plan.outer 自己*/, instance_id=<adopted>, revision=1))` → 抛 `StoreConflict: method instance mi-70fab16e… already stored … UNIQUE constraint failed: method_instances.mission_id, method_instances.instance_id`（探针 `test_probe_a_d_e.py::test_A`）
- 复现 2（端到端、默认 `max_root_review_repairs=1`）：两方法库（outer + alt），根评审恒 FAIL，Planner 用 P2.3j 自己的 `_planner_replaces`（取第一条 `rejected_by_root_review=false`）：rev 1 outer 被拒 → 修复轮 → rev 2 alt → 被拒 → **修复轮再开**（rev 2 计数为 0）→ 包里 outer 不再标记 → Planner 退 alt 上 outer → id 与 rev 1 的 RETIRED 行相同 → `StoreConflict` 每周期重复抛出（探针 `test_probe_e2.py`：`errors` 连续 3 个周期同一异常，`status ACTIVE`, `stop None`, `revisions [1, 2]`, `repairs [1, 2]`）。真实 `run()` 里第一次即崩出主循环
- 建议修法（不改 contracts）：
  1. `compile_proposal`：对 refine 产出的 draft，若 `semantics.method_instance_state(mission, draft.instance_id)` 已存在（任何状态），以具名 `ContractError`/`PlanCommitRejected("METHOD_INSTANCE_RETIRED", …)` 拒绝，并进 `_planning_rejected` 梯子（与 `proposal_not_grounded` 同路）；同时 retire+refine 时若 `operation.method_ref == 被退实例.method_ref` 直接拒绝（同一方法同参数换汤不换药）
  2. 防线：`_collect_plan_hierarchical` 接住 `StoreConflict`（或 `StoreError` 中非 `StoreBusy` 的部分）→ `_planning_rejected(reason="plan_commit_refused")`，不让一次坏提案杀掉整个 `run()`

### P1-1 修复/合成的「有界」按 plan revision 计，跨 revision 无界；被拒历史不累计

- 位置：`event_handler.py` L7288–L7295（`used = _root_review_repairs(mission, revision)` 每 revision 独立）、L7317（记录键含 revision）、L7353–L7361；`hierarchical_dispatch.py` L2712（`detail.plan_revision != network.plan_revision → continue`，旧 revision 的拒绝不再列入 `rejected_refinements`，也不再打 `rejected_by_root_review`）；`goals_needing_method` 的 `synthesis_round = plan_revision+1` 同样每 revision 一轮
- 复现：同 P0-1 复现 2：`repairs [1, 2]`、`HierarchicalRootReviewRejected` 2 次、Planner 2 次；若两方法 id 不撞（例如每次合成出新方法，或 P0-1 修成「拒绝」后 Planner 换第三种方法），链条 rev1→rev2→rev3… 只受 `max_expanded_nodes`（默认 4096）与 token 池约束——而 P2.3j 的 `_held_by_retired_row` 恰恰让被退叶子未花的 ceiling 回到池里，脚本化叶子 settled=0 时池永不耗尽。`max_root_review_cuts` 亦是按 requirements revision 计，每次验收推进 revision 后重置，不构成跨 revision 的界
- 与文档矛盾：CHANGELOG L57「被拒历史不跨修订累计（…默认 `max_root_review_repairs=1` 下走不到）」——实测走得到
- 建议修法：(a) `_root_review_repairs` 改为按 Mission 累计（或对同一 occurrence 的修复链累计），配置语义改为「每 Mission 最多 N 次根评审修复」；(b) `rejected_refinements` / `method_library(rejected_refs=)` / `method_applicability` / `goals_needing_method` 读取该 occurrence 上**所有** `PlanningRejected{root_review_rejected}` 的 `method_ref`（不按 revision 过滤），候选数扣除全部被拒方法；(c) 测试：两方法库 + 恒 FAIL → 第二次拒绝后诚实 FAILED，`root_review.repairs_used` 与 Mission 级上限一致

### P1-2 `retire_method` 放行范围过宽；`REQUEST_STOP_THEN_RECONCILE` 只是标签，运行中工作既不停也不回收

- 位置：`hierarchical_dispatch.py` L3455–L3506（只要求被退实例是该 occurrence 的 ADOPTED 实例，不要求它在 `rejected_refinements` 里）、L3585–L3589（任何退方法一律盖 `REQUEST_STOP_THEN_RECONCILE`，绕过 `RETAIN_IF_BINDINGS_UNCHANGED` 的 `RUNNING_WORK_NOT_RECONCILED` 拒绝）；`plan_commits.py` L849–L908 `_revoke_running_work` 只 bump dispatch_generation + `mark_dirty(reason="dispatch_generation_revoked")`；`htn_store.list_dirty` 在 `src/agent_orchestrator/orchestrator/` 下**无任何调用者**；被退叶子的 Task 行状态、Attempt 状态、ledger 预留均不动
- 复现（探针 `test_probe_b.py`）：`committed(demand=True)`（无根评审、无拒绝）+ 注册 alt + 给一片叶子插入 RUNNING attempt 并在其账户 `reserve(500)` → `world.plan(retire+refine alt)` → **committed**；事件 `running_work_policy=request_stop_then_reconcile`、`revoked_dispatch_generations` 两叶；之后旧叶 Task `READY`、attempt `RUNNING`、`reserved 500` 仍在、dirty 两条无人消费；`budget_conservation.held_elsewhere=500` 而该账户 ceiling 仍是 100 000，新叶各获 99 750（等式对在途工作偏乐观；实际超支仍由 mission 账户链兜底）
- 可达路径：任何在已提交计划上开的 Planner 轮（D5-B 嵌套细化、`method_synthesis` 阶段、梯子续轮）都能对根或任意已细化 occurrence 提 retire+refine，不必先有根评审拒绝
- 建议修法：`compile_proposal` 只对 `rejected_refinements` 中的实例接受 `retire_method`（P2.3j 的用例正是如此），其余照旧拒绝；或至少在 `_revoke_running_work` 里对被退子 occurrence 存在非终态 Attempt 时拒绝 `RUNNING_WORK_NOT_RECONCILED`（保持默认策略），把 `REQUEST_STOP_THEN_RECONCILE` 留到真的实现 stop+reconcile（消费 dirty、取消 attempt、释放预留、Task 行 CANCELLED）的切片
