## 1. P0

### P0-1 D5-A / D5-B 新开的 Planner 轮次没有接 `BudgetExhausted`，整个 `run()` 循环随之崩溃

**证据**

- `_repair_after_root_review`（`event_handler.py:6443-6509`）与 `_refine_open_compounds`（`2220-2283`）都以 `return await self._try_planner_intent(...)` 收尾。
- `_try_planner_intent`（`2135-2184`）只捕 `GraphIntegrityError` / `RoutingUnavailable` / `ContextRejected`；`_create_planner_intent`（`2433+`，第 87 行 `reservation=self._reservation(self._config.planner_reserve_tokens, …)`）在 Mission 账户不足时抛 `BudgetExhausted`（`governance/budgets.py:39`，`StoreError` 子类）。
- 第一轮规划有保护：`_start_planning`（`2196-2216`）包了 `except BudgetExhausted → fail_planning(budget_exhausted)`。两个新入口**没有**。
- `_cycle`（`1961-1975`）只吞 `StoreBusy` / `CommitRejected` / `IllegalTransition`；`run()` 的 while 循环（`1626-1627`）直接 `await self._cycle()`，没有外层 try。

**复现**（`<scratch>/probe/test_probe_budget.py`、`test_probe_loop.py`，夹具 = `test_root_review_repair._rejected_world` 但 `tokens=100 < planner_reserve_tokens=4000`）：

```
D5A  _advance_root_review → BudgetExhausted('tokens requested 4000, remaining 100')  status=ACTIVE
D5B  _refine_open_compounds → BudgetExhausted(...)                                    status=PLANNING
RUN  loop.run(max_cycles=4) → BudgetExhausted 逃出 run()；events 尾巴 = [...RootReviewRejected, TaskUnblocked, PlanningRejected]，无 MissionFailed
```

D5-A 的触发点恰好是「4 个叶子 + 4 次 critic + 1 次根评审都花完之后」，是一局里账户最紧的时刻；`PlanningRejected{root_review_rejected}` 已经落库（`used=1`），进程却带着 traceback 退出，Mission 停在 ACTIVE，既没有 `MissionFailed` 也没有 stall 记录——比 0.12.0 的「记下、return False」还差。runner 每局一个进程，表现就是该局崩溃、`mission_status` 不可读。

**建议修法**：两处各包一层 `except BudgetExhausted`，按 `_start_planning` 的 detail 结构记账；但**不要**调 `fail_planning`（它对 ACTIVE Mission 也会走 `next_mission(FAILED)`，把「已提交计划」判死）——D5-A 情形应记一条 stall（复用 `record_cut_budget_spent` 同型的「一次，然后沉默」）或 `fail_mission(stop_reason=BUDGET_EXHAUSTED)`，让 idle-stall 路径如实收口；D5-B 在 PLANNING 情形可以沿用 `fail_planning(budget_exhausted)`。各补一条「账户 100 token」的测试（探针可直接改成回归）。

## 2. P1

### P1-1 D2b 只做了半程：合成轮能开，合成方法准入后没有任何东西再问 Planner

**证据**

- `_try_planner_intent` 全部 5 个调用点：`2190`（deferred 重试）、`2197`（`_start_planning`，仅 CREATED）、`2283`（`_refine_open_compounds`，要求 `active_plan_revision` 非空——PLANNING 阶段没有修订，`2247-2249` 直接 `return False`）、`3585`（`_planning_rejected` 梯子）、`6509`（D5-A）。**没有一个由合成结果触发**。
- `_collect_synthesis…`（`3770-3800`）：`apply_synthesizer_reply` → `record_synthesis_outcome` → `_settle_intent`，到此为止。
- 真实 L3 序列（`H-L3-C1-r0/orchestrator.db`）：observations 表里 `code.test-is-failing` 已被 `code.test-observer` 记了 **2** 条（`polarity=0`），`code.regression-commit-known` 同样 2 条——按 N=2 第二周期就饱和；但 events 是 `5 MethodApplicabilityAssessed → 11 PlanningRejected → 17 PlanningRejected → 18 MissionFailed`：planner#1 被拒时 `_planning_rejected` **立刻**创建 planner#2（包在合成之前封好，`2357` 行 `rejected=…`），planner#2 回复被拒 → `ordinal 2 ≥ max_planning_attempts=2` 且 PLANNING → `fail_planning`。
- 即便 runner 按 HANDOFF 传 `max_planning_attempts=3`：planner#3 在 planner#2 被拒的同一次 collect 里创建，与 synthesizer 的回复**竞速**；合成先回则 planner#3 的包含新方法，否则 planner#3 再拒 → 死。谁先回取决于两个模型调用的延迟，不是机制。

**测试覆盖**：`test_evidence_saturation.py` 7 条全部止于 `goals_needing_method`；没有任何测试走到「synthesizer admitted → 新 Planner 轮 → `PlanRevisionCommitted`」。journal §2b 把 D2b 的红测试写成「活锁：永远返回空」，修的是 `goals_needing_method` 的返回值，不是活锁本身。

**建议修法**：`_collect_synthesis…` 在 `admitted=True` 且 Mission ∈ {PLANNING, ACTIVE} 且无在途 plan intent 时，`_try_planner_intent(self._next_planning_ordinal(mission_id))`；这一轮不该受 `max_planning_attempts` 梯子约束（否则 PLANNING 下它仍会被 `fail_planning`），最简单是在 `_planning_rejected` 里把「上一轮 PlanningRejected 之后有 `MethodSynthesisAdmitted`」视同梯子重置，或者给合成后的轮次一个独立上限。补一条 scripted 端到端测试：planner 脚本第一轮选 NEEDS_EVIDENCE 方法、synthesizer 脚本给一个可用方法、planner 第二轮采用它 → `PlanRevisionCommitted`。

## 3. P2

### P2-1 D5-A 的有界性：单修订有界成立，跨修订靠「裁剪预算」兜底，且无测试

- 每修订 1 次（`_root_review_repairs` 按 `PlanningRejected{root_review_rejected}.detail.plan_revision` 计数，`6491-6501`）——`test_a_second_cycle_on_the_same_revision_does_not_ask_again` 钉住。
- 连续 REJECT 的链：修复 → 新修订 → 新叶验收 → `CONTRIBUTIONS_MOVED`（`root_review.py:528-530`）→ RECUT_REQUIRED → 新裁剪绑定**同一** `requirements_revision`（根准则内容不变时 `_requirements` 复用同号，`876-887`）→ `cuts_for_revision` 累积 → 第 `max_root_review_cuts`(默认 3) 次后 `CUT_BUDGET_SPENT` → idle stall。所以总链 ≤ 3 次裁剪 ≈ 2 次修复，另受 token/attempt 预算约束。**这是读代码推出来的，没有构造「连续 REJECT」的测试跑到 stall**（journal 偏差 2 承认没做整链）。
- 建议：补一条 scripted 链测试（planner 脚本给不同方法、reviewer 脚本恒 REJECT+blocker），断言终态是 `HierarchicalRootReviewCutBudgetSpent`/stall 而非循环。

### P2-2 修复轮/细化轮自己的拒绝理由不落库

`record_planning_rejected` 的幂等键是 `{mission}:planner:{ordinal}`（`commit_service.py:2749`）；D5-A 先用该 ordinal 写了 `root_review_rejected`，随后这一轮的真实拒绝（`proposal_unreadable` / `proposal_not_grounded`）被同键吞掉——`test_a_rejected_repair_round_does_not_kill…` 把这写成「One record, not two」当作特性。后果：若 `max_planning_attempts > ordinal`，下一轮的 `rejected` 反馈里没有「上一轮为什么被拒」。建议 D5-A 的 findings 记录改用独立键（如 `{mission}:root-review-repair:{revision}`）或另起事件名。

### P2-3 「梯子各是一轮」不准确

`_planning_rejected`（`3583-3585`）对 ACTIVE Mission 仍走 `ordinal < max_planning_attempts → _try_planner_intent(ordinal+1)`：runner 传 3、修复轮 ordinal=2 被拒 → 立刻开 ordinal 3。实际上限是 `max_planning_attempts − ordinal + 1` 轮 + 预算，不是 journal 写的「一轮」。行为可接受，但文档与 `_repair_after_root_review` docstring 要改口。

### P2-4 修复轮/细化轮遇 `RoutingUnavailable` / `ContextRejected` 的处理是为 PLANNING 写的

- `RoutingUnavailable` → 进 `_deferred_planning`，但 `_prune_deferred`（`2131-2133`）对 `status is not PLANNING` 的 Mission 直接 pop → ACTIVE Mission 的修复轮静默丢失，而 `used` 已记 1，不再有第二次。
- `ContextRejected` → `fail_planning(context_rejected)`，对 ACTIVE Mission 照样 `next_mission(FAILED)`（`commit_service.py:2762-2770`），与「committed plan stands」矛盾。

### P2-5 D5-B 的「每修订一轮」是进程内状态

`self._refinement_rounds`（`379`）不落库；进程重启 / 多实例下同一修订会再被问一轮。有 `_next_planning_ordinal` 探测在，不会重复派同一 intent，但会多花一次模型调用。建议改成读事件（像 `_root_review_repairs` 那样）。

### P2-6 变异 M05 存活：criterion-linked 但 optional 的端口行为未被钉住

`_merge_ports` 只并入 `port.required` 的端口（`accepted_outputs.py:284-291`），而 `declared_output_ports_for` 对集合里每个端口一律报 `required: True`。把 `if port.required` 去掉，full_target 2687 全绿（见 §5 变异表）。两种语义（optional 端口不进集合 / 进集合但 required=False）都说得通，但现在没有测试说是哪一种。

### P2-7 `declared_output_ports(network, …)` 用索引对齐找 binding

`accepted_outputs.py:128-136` 用 `zip(network.task_bindings, network.occurrences)` 取同下标的 binding。`HierarchicalDispatch.network()` 构造时确实按 occurrences 顺序（`hierarchical_dispatch.py:801`），但 compiler 输出的快照（`3140` `compilation.task_bindings`；`compiler.py:1113-1135` 是「旧 bindings + 新 bindings」拼接）没有这个保证。`TaskNetworkSnapshot.binding_for_occurrence(producer)`（`task_network.py:526`）就是干这个的。目前生产路径无人调用网络版（`check_declared` 只剩注释），所以只是隐患。

### P2-8 D5-A 测试没有证明「findings 进了 Planner 包」

`_create_planner_intent` 只在 `ordinal > 1` 时把 `_planning_rejections` 放进包（`2357`、`2475`）；`_rejected_world` 夹具的计划是 `apply_planner_reply` 直提的，修复轮拿到 ordinal **1**。探针（`test_probe_loop.py::test_repair_package_carries_findings`）：`ordinal=1, findings_in_package=False, reason_in_package=False`。生产序号 ≥ 2 所以功能成立，但 `test_the_findings_travel_to_the_planner_as_durable_feedback` 只证明事件存在。建议夹具第一轮走 intent，或直接断言包内容。

### P2-9 D4 的口径：no_progress 上限对分层 Task 事实上不再生效

诊断说「`ManagementDecided{rejected}` 计入 no_progress」并不准确——`no_progress_count`（`commit_service.py:3788-3796`）只数 attempt 的 failure reason；真正烧额度的是 manager 收集路径末尾的 `_enforce_no_progress`（`5555`）。D4 短路后分层 Task 不再进这条路，重复验证失败只受 `max_attempts` 约束（`_decide` 的 max_attempts 停止）。结果是诚实的，但 HANDOFF/CHANGELOG 里「不再烧 no_progress 额度」应改成「no_progress 上限不再作用于分层 Task」。

### P2-10 非终结步的 criterion-linked 情形无独立测试

`criterion_linked_occurrences` 读 `covered_by`，`coverage_from_slots` 对带 `child_step` 的 link 解析到该 slot（`compiler.py:731`），逻辑覆盖非终结步；但所有夹具（`_outer`、`_unlinked_method`、`code.fix-by-patch`）的 link 都恰好落在 finalizer 上。建议加一个「link 指向非 finalizer 步」的夹具。
