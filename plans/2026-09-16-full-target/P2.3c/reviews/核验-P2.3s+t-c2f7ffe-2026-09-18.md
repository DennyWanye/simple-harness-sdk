## 2. 重点审查

### (a) 取消兄弟 attempt —— ✅ 范围正确；预留走既有 `_close_attempt`；不与终态 hook 双触发

`reconcile_retiring_instance`（`hierarchical_dispatch.py:3936-4005`）只遍历**被退役实例**的 `child_bindings`：

1. OPEN attempt（PENDING/CLAIMED/RUNNING/SUBMITTED/VERIFYING）先 `_close_attempt(..., CANCELLED, reason=method_retired_by_repair)`；
2. 外方未过期 lease（`holder != owner` 且 `expires > now`）不抢，记入 `remaining`，整叶跳过；
3. P2.3q 可复用 occurrence（`_repair_read_only_share_index`）`keep_task`：不 `TaskCancelled`，但残留 OPEN attempt 仍关；
4. 非复用且 READY/ACTIVE/VERIFYING → `TaskCancelled{method_retired_by_repair}`；TERMINAL / BLOCKED 不取消任务。

不会取消其他实例的孩子。可复用叶已是 COMPLETED（CURRENT Acceptance），即使 share index 抛错把 `reusable` 清空，也会被 `TERMINAL_TASK` 跳过任务取消。

预留：`_close_attempt`（`commit_service.py:1805-1843`）对非 SUBMITTED 且无 UNKNOWN 的 reservation 立刻 `settle_subject`；SUBMITTED 留到 collect。随后 `_release_cancelled_repair_work` → `_release_attempt(cancel=True)` 只解绑/取消 SDK turn（`_released` 幂等），不二次结算。Planner 收集成功路径（`event_handler.py:5064`）、根评审修复打开、只读升级、Deferred 重试四处都调了 release。

与 P2.3p/r：reconcile 发生在**中途**，不走 `_prepare_terminal_ledger`。终态 `fail_mission` 才 `_prepare`（跳过已 SETTLED）再 `_cascade_stop`。不是双触发。

安全网 `_check_retirement_is_a_repair` 仍点名 `running_work_not_reconciled`（变异 M1 打到）。RETRY_WAIT 不在 OPEN 集、状态机无边到 CANCELLED（journal 已记，本片不改 contracts）。

### (b) RepairCompileDeferred —— 每 cycle 轮询重试；悬挂无专用具名停机（P2）

唤醒：不是 AttemptCancelled 事件监听。`_cycle_inner` 每圈调 `_retry_deferred_repair`（`event_handler.py:2322, 2741-2795`）；stall 确认在未用尽时也会先 retry。blocker 消失后 `remaining==()`，用**同一提案文本**再 `apply_planner_reply`。成功写 `RepairCompileResumed`（key `{mission}:repair-resumed:{proposal_id}`）。有 pending 时 stall 路径不再开新 Planner。

同一提案 vs P2.3n/j / StoreConflict：Deferred 发生在 compile **之前**，首次未提交。重试时实例仍须在 `adopted_instance_ids`，否则 `repair_compile_pending` 返回 None。`retirement_not_a_repair` / `StoreConflict` 被 catch 后只 `_note`，pending 不销；若此时已无 ACTIVE 叶，stall 确认 → `planning_failed`。不会无限 Planner。测试 `test_a_live_foreign_lease_defers…` 只断言登记 Deferred、不抢 attempt；**blocker 结束后提交未 e2e**（P2-2）。

悬挂：`_record_hierarchical_stall` 见任一 ACTIVE 叶就 `continue`（`event_handler.py:1967-1969`），外方 lease 占着 RUNNING/ACTIVE 时 stall 确认**不会**走到 `planning_failed`。SDK `Budget.max_runtime_seconds` 默认 `None`，墙钟只在 Host 写入时生效（第 5 批 runner 7200 s → `budget_exhausted`）。同进程 C1-r0 的 verify 与 Orchestrator 同 owner，走取消而非 Deferred，本批失败链不受影响。建议（不修）：pending 且 remaining 非空超过 N cycle / 墙钟 → 具名 `planning_failed{repair_blocked_by_running_work}`。

### (c) 具名停机分工 + 事件序列推演 —— ✅ 目标局不再 `no_dispatchable_work`

判定（`event_handler.py:2162-2243`，合并决议）：

1. `REVIEW_REJECTED` 且 `repairs_used >= max_root_review_repairs ≥ 1` → `root_review_repairs_exhausted`，`admitted_not_dispatched=[]`（t 优先）；
2. 否则 pending Deferred 或未处置 `rejected_refinements` → `planning_failed`（detail `repair_blocked_by_running_work` 或既有修复理由）；
3. 真无活修复才 `no_dispatchable_work`。用尽时**不再**重试 deferred。

`_root_review_repairs_are_exhausted` 认 status 字符串 `"REVIEW_REJECTED"` + 全局 `repairs_used`（Mission 界，不是单 revision）。变异 M4 关掉它：`test_two_root_review_rejects…` 回到 `no_dispatchable_work`，`test_repeated_rejections…` 落到 `planning_failed`——证明 t 的具名停机是 C1-r1 的必要门，不是文档装饰。
