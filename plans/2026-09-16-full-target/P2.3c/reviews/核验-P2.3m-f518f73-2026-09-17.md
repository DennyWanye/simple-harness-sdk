## 2. 重点审查（P0/P1 逐条）

### (a) 同哈希豁免能否被利用 —— ✅ 键是 path+hash，不是裸哈希

`read_only_rewrites`（`occurrence_tasks.py:399-406`）：

```
artifact.path in initial
and artifact.content_hash != initial[artifact.path]
and allowed.get(artifact.path) != artifact.content_hash
```

`_accepted_path_hashes`（`event_handler.py:7743-7761`）按 **path → hash**，COMPLETED 叶的全部 listed 产物（不限于端口），后写覆盖。

独立探测（恢复后的源，非测试）：

| 情况 | 结果 |
|---|---|
| 同 path、同已完成叶 hash | 豁免 `[]` |
| 同 path、新 hash（r1） | 拒绝该 path |
| **异 path、同已完成叶 hash**（把 collector 字节写进 `tests/test_public_collector.py`） | **仍拒绝**（`['tests/test_public_collector.py']`） |
| 改写 initial 里、从未被完成叶列出的种子文件 | 拒绝 |

所以「改写成某个已验收产物的内容但路径不同」不能豁免；「改写非产物的种子文件」也不能。新文件（不在 `initial`）仍允许——只读叶交 REPORT.md 的既有口径。

数据源是 **COMPLETED 叶 listed artifacts**，不是 CURRENT `acceptance_outputs`。对 C1-r0（apply-patch 把 `metrics/collector.py` 列进结果、不在 `patch` 端口）这是必要的；声称「已验收产物」略宽于实现「完成叶产物」。见 P2-1。

分层门：`accepted_hashes` / `consistent` 仅 `new_mode is not None`（`event_handler.py:4907-4964`）。实施者说「同哈希过滤套到 legacy 收集会挂住 `run()`」——代码已把门，legacy 定向 + 全量均绿。legacy 收集语义未改。

### (b) 取消叶后升级路径 —— ✅ 触发修复轮/合成轮，不是 planning_failed

顺序（`event_handler.py:4923-4946` + `_escalate_read_only_rewrite:7743+`）：

1. `ResultRejected{read_only_leaf_rewrote_workspace}`；attempt 已 `_release_attempt`。
2. 计数 ≥ `MAX_READ_ONLY_REWRITE_REJECTIONS=2` → `_cancel_task_entity`（ACTIVE→CANCELLED，合法边；RETRY_WAIT 不是 Task 态，叶停在 ACTIVE 上取消，避免 P2.3j `running_work_not_reconciled`）。
3. 已用修复 ≥ `MAX_READ_ONLY_REWRITE_REPAIRS=1` → `fail_mission(NO_DISPATCHABLE_WORK)`，detail 带 `read_only_leaf_needs_write`。
4. 否则 `record_planning_rejected(reason=read_only_leaf_needs_write)`（**直接写事件，不经 `_planning_rejected` 梯子**）+ `_planner_round_on_committed_plan(phase=read_only_rewrite_repair)`。
5. `REPAIR_REASONS` 含该理由（`hierarchical_dispatch.py:259-263`）；`rejected_refinements` / `repair_round_answered` / 包段与 P2.3j 共用。
6. Planner 先答；无新 revision 且 `review_package_id` 空 → `goals_needing_method` 强制合成（`3237-3242`），不把剩余 NEEDS_EVIDENCE 库方法当成「再看一眼」。
7. 合成拒绝且已有该修复记录 → `fail_mission(NO_DISPATCHABLE_WORK)`（`4457-4468`），不是 `planning_failed`。
8. stall 出口合并 `_read_only_rewrite_stop_detail`（`2008-2009`）。

端到端：`test_two_new_rewrites_escalate_to_planning_with_named_feedback` 断言恰好 2 次拒绝、有 `PlanningRejected`、合成 `admitted=True`、verify 只有 attempt 1/2、停机不是 `budget_exhausted`。`test_persistent_rewrites_…` 断言具名停机、`reserved==0`、无 HELD、守恒 `remaining+reserved+settled==pool`。

### (c) 401 快速失败 —— ✅ 按 error_code；5xx/超时不误杀

判定：`_error_codes` 只收键 `error_code` / `code` / `kind` 的字符串（`model_router.py:48,221-235`，无子串、不读 `status_code`）。编排侧集合：

```
DEFINITE_AUTH_CODES = {provider_authentication_failed, provider_payment_required}
```

对应 runtime `ProviderAuthenticationError` / `ProviderPaymentRequiredError`（HTTP 401/402 在 provider 层已映射）。`ProviderServerError`（5xx）与超时 UNKNOWN **不在**该集合。

三条接线：

1. `_collect_plan`（`4071-4096`）：plan / synthesizer / root_reviewer；分层 + 非 COMMITTED + 鉴权码 → PLANNING 则 `fail_planning(RUNTIME_UNAVAILABLE)`，ACTIVE 则 `fail_mission`。不爬梯子。
2. Worker FAILED 收集（`4708-4738`）：`is_hierarchical` 门；`stop_task(RUNTIME_UNAVAILABLE)` **连带 Mission FAILED**（`commit_service.py:5479-5543`）。legacy 不进。
3. `_resolve_provider_blocked_service`（`6803-6820`）：`auth_blocked` 立即 give-up，不等 300s。`_provider_blocked` 仍要求 UNKNOWN + `kind=provider`，5xx FAILED / 超时 UNKNOWN 的既有分流不变。

P2.3f 重交接条件未改：UNKNOWN provider wait → 300s → 一次 rehandoff。本片未把 5xx 并进 `DEFINITE_AUTH_CODES`。瞬时 5xx 若 runtime 已标 FAILED（`ProviderServerError` 本就在 `_DEFINITE_PROVIDER_FAILURES`），**修前也不走 P2.3f**——P2.3f 只吃 UNKNOWN。本片没有把瞬时错误改成快失败。

缺口：编排测试目录 **零条** 401 用例（只有 conformance 的 provider 契约）。Critic 收集仍把非 COMMITTED 当 `critic turn failed` 重试，未接 401 快失败。见 P2-3。
