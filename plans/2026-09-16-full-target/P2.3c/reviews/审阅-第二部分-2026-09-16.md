#### F1 · 派发闸门可被整条绕过：未调 `install_hierarchical()` 的部署让 hierarchical Mission 走 legacy `allocate()`

- 位置：`src/agent_orchestrator/orchestrator/event_handler.py:1016-1021`
  ```python
  def _new_mode(self, mission: Mission) -> HierarchicalDispatch | None:
      if self._hierarchical is None or not is_hierarchical(mission):
          return None
      return self._hierarchical
  ```
  配套位置：`orchestrator/plan_commits.py:958-968`（`_materialise_occurrences` 在
  `commit_plan_revision` 里**无条件**执行）、`event_handler.py:5268-5300`（`_decide` 的
  `if new_mode is not None: … else: plan = allocate(…)`）、`event_handler.py:5448-5465`
  （`_next_attempt` 的 admission 复检也在 `if new_mode is not None` 分支内）。

- 问题：物化（写 Task 行）由 **CommitService** 做，闸门（allocate_v2 / admission 复检 /
  根 Resolution 门）由 **Orchestrator 的 `_hierarchical` 字段**决定。二者没有任何耦合。
  `install_hierarchical` 在整个 `src/` 里**零调用**（只在 tests 里），journal §10 也承认
  部署侧 `PlanningWorld` 装配还不存在。也就是说，今天没有任何真实部署路径是接上闸门的，
  而 Task 行已经开始被写进库。

- 后果：P2.3b 时代 `_new_mode is None` 是无害的（库里根本没有 Task 行，`_decide` 在
  `if not tasks` 就返回）。本片之后，同样的配置会把 occurrence 行交给 legacy `allocate()`：
  - 按 `TaskStatus.READY` 串派发，**DATA 消费者在生产者未被验收时就被派出去**——正是本片
    宣称修掉的 P2.3b blocker (b)；
  - `_next_attempt` 的 TG §8.3 复检被跳过；
  - `_root_resolution_formed` 也被跳过（`settled` 走 legacy 的"全 COMPLETED"分支）。
  这就是 §18.5 rule 1 明令禁止的 silent half-mode：一个 Mission 一半按新模式提交计划、
  一半按旧模式派发。

- 证据：本片自己的 `test_mutant_allocating_on_the_ready_string_would_dispatch_the_data_consumer`
  断言的就是"legacy 会派、闸门不会派"这个差，只是它没问"什么时候会真的走 legacy 那一侧"。

- 建议修法（择一，倾向第一条）：
  1. **fail-closed**：`_decide` / `_next_attempt` 在 `is_hierarchical(mission)` 为真而
     `self._hierarchical is None` 时**拒绝派发**并记一个新事件（例如
     `HierarchicalAssemblyMissing`），而不是静默回落 legacy。这与本片自己在
     `require_planning_world()` 上的选择（"a deployment without a PlanningWorld must fail
     here rather than quietly hand the model the legacy DAG package (§18.5)"）完全同形，
     只是漏了调度这一侧。
  2. 或者让 `Orchestrator` 在看到 hierarchical Mission 时自动装配（需要第三部分的
     `PlanningWorld`，所以短期只能走 1）。
- 测试覆盖：**无**。§12 的四条 legacy 零回归只证明 legacy Mission 不受影响。建议补：
  "hierarchical Mission + 未装配 → 一个 Attempt 都不创建"。
- 审阅探针（副本上实跑、10 条全绿，见 `scratchpad/p23c-review-probes.py`）：
  `test_probe_without_install_hierarchical_the_legacy_allocator_grants_the_data_consumer`
  证明同一批行上 `allocate()` 同时授予 `plan.leaf` 与 `plan.review`，而
  `admissions().readiness` 只有 `plan.leaf`；
  `test_probe_install_hierarchical_is_never_called_in_src` 证明 `src/` 里只有它自己的定义。
- 旁证：变异 **M17 存活**——`_next_attempt` 的 admission 复检（TG §8.3，本片新加的第二道门）
  删掉之后整套 2272 条一条不红。两道门里有一道没有任何证据说它在工作。

#### F6 · 正向完成路径不可达，且被零条测试触及：`judge_mission` 对 compound 行永远报错；`judge_mission` 本身没有模式门

- 位置：`orchestrator/commit_service.py:4717-4728`
  ```python
  if not tasks or any(task.status is not TaskStatus.COMPLETED for task in tasks):
      raise CommitRejected("mission judgment requires every live Task to be COMPLETED")
  ```
  `orchestrator/occurrence_tasks.py`：compound 行 `status=TaskStatus.BLOCKED`，既不会
  COMPLETED 也不会 CANCELLED。
- 后果一（活性）：即使根 Resolution 成功形成，`_decide` 接着调 `_judge` → `judge_mission` →
  `CommitRejected`（被 `_cycle` 吞掉），Mission 永远停在 ACTIVE。本片把阻塞点从"永远不 settled"
  搬到了"settled 之后 judge 必拒"，而 journal §12/§13 没有把它记为偏差。
- 后果二（安全）：`judge_mission` 是 `CommitService` 的公开入口，**没有任何模式检查**（对比
  `commit_graph_change` 在最前面就查 `semantics_of(mission) == HIERARCHICAL_SEMANTICS`）。
  一个只含 primitive 的 hierarchical Mission 可以绕过根 Resolution 直接被判成 COMPLETED。
  今天挡住常见情形的只是"compound 行恒 BLOCKED"这个巧合，不是设计。
- 测试：§8 的 9 条根验收测试**全部停在 `ROOT_REVIEW_NOT_READY`**（`root_review_ready` 为 False
  就早返回），§13 的真实循环测试也只断言"没有 Resolution 就不 COMPLETED"。
  `attempt_root_resolution` 在 `root_review_ready` 之后的**全部代码从未被执行过**——
  `root_resolution_inputs` 的 package / record / witness 查找、`read_set_for_root`、
  `CompoundFacts` 组装、`ResolutionPrincipal` 转换，一行都没跑。
- 建议：
  1. `judge_mission` 最前面加模式门：hierarchical Mission 必须已有根 GoalResolution，
     否则 `CommitRejected`（与 `commit_graph_change` 同形，并记一个新事件）；
  2. compound 行在其 Resolution 形成后转 COMPLETED，或明确把 compound 行排除在
     `judge_mission` 的 live 集合外（无论哪种，都要写成规则而不是巧合）；
  3. 补一条 happy-path 端到端：手工放好 MISSION_FINAL package / official record /
     ACCEPT witness + 子 Acceptance，跑通一次根 Resolution 并断言 Mission 到 COMPLETED。
     这是本片最缺的一条测试。
- 探针 `test_probe_judge_mission_has_no_mode_gate` 与
  `test_probe_judge_mission_cannot_complete_a_plan_that_has_a_compound_row` 已实跑证实
  （后者拿到的正是 `CommitRejected: mission judgment requires every live Task to be COMPLETED`，
  Mission 停在 ACTIVE）。
- 旁证：变异 **M09 存活于一切行为测试**（只被一条源码字符串测试抓住）——§13 那条"真实循环"

  `settled` 那一步就短路了，根本走不到门前。

必须先修的两条：**F1**（派发闸门可整条绕过）和 **F7**（跨 revision 的预算守恒没有任何测试，
M04 证明把等式改回"只写本网络"整套一条不红——§21.5 的硬性不变量之一今天是没有证据的）。
其余 F2–F6、F8–F10 应在本片或第三部分开工前一并处理，
其中 **F6 的 (3)「补一条根 Resolution 的 happy-path 端到端测试」是性价比最高的一条**——
F4、F5、F6 三个发现全都藏在同一段从未被执行的代码里，一条 happy-path 测试会同时照到它们。

这一片的工程判断我认可：三道 compound 门、admission 不是带标志的拒绝、回执从库复读、
守恒等式写在"库里已有的"而不是"本网络"上、迁移 17 只增不改、legacy 分支逐字不动——
这些都是对的，而且变异测试证明它们是承重的、有测试保护的。
真正的风险不在这些判断里，而在"闸门与物化不同源"和"根验收整条 happy path 零执行"这两处。
