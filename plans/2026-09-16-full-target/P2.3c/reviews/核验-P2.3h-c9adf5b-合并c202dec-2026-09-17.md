## 2. 缺陷

### P1-1 `methods.json` 改定义未升版本：已有方法库的 store 在 P2.3h 下无法再建 PlanningWorld；旧 mission 记录的 `code.fix-*@1` 指向另一份字节

- 位置：`src/agent_orchestrator/planning/htn/seed_methods/code/methods.json`（`code.fix-by-patch` / `code.fix-by-revert` / `code.fix-by-assessed-revert`，`method_version` 均仍为 1）；触发点 `src/agent_orchestrator/storage/htn_store.py:315-321`（`register_method`：同 (id, version) 不同 `content_hash` → `StoreConflict("… already stored with different content; a changed definition needs a new version")`），经 `planning/htn/world.py:459-489`（`admit_domain` → `publish_methods`）在 `build_planning_world` 内抛出。
- 原理：`MethodContract.method_ref().content_hash = content_hash_of(self.to_json())`（contracts/htn.py:996-1001），criterion_links 属于契约字节，`fec821b9…`（旧）→ `1ffbc867…`（新）。`seed_content_hash(id, version)` 只用于文件内 `{id, version}` 引用的补全，不影响方法自身的 ref。
- 复现（脚本 `scratchpad/p23h-out/repro_d.py`，用 `git archive 8b8466d` 取出的旧 seed 目录）：同一 sqlite store 先 `build_planning_world(root=旧seed)` 再 `build_planning_world(root=SEED_ROOT)` → `StoreConflict: method code.fix-by-assessed-revert@1 is already stored with different content; a changed definition needs a new version`。
- 影响：① Host 若复用部署级 store（任何跑过 code 域 mission 的 DB），升级到 P2.3h 后新 mission 在建世界时直接异常，不是优雅拒绝；② 旧 mission 的 `MethodInstanceDraft.method_ref.content_hash` / plan revision 引用 `code.fix-*@1`，在新库里 `get_method(id, 1)` 读到的是另一份契约，回放/复核会 hash 不符。CHANGELOG/HANDOFF 只写了「runner FREEZE-candidate 需重生成」，没有覆盖这两点。
- 建议修法：三个方法 `method_version` → 2（旧 v1 是否保留在文件里由发布方决定：保留则旧 store 无冲突、新 mission 由准入/规划选到 v2；不保留则至少在 `publish_methods` 处把 `StoreConflict` 变成带方法名的明确拒绝而非裸异常），并在 CHANGELOG「口径」补「已有 store 的 code 域方法库需迁移」。同时加一条测试：同一 store 先装 8b8466d 版 code 域再装当前版不得抛异常（或明确抛可读拒绝）。

### P2-1 Worker 上下文块接线（event_handler.py 7565–7583）无测试覆盖，变异存活

- 我的变异 M6（把 `if carried:` 改成 `if False and carried:`）在 `test_root_review_evidence.py` 27 条与整个 `tests/` 目录下**存活**：`grep -rl carried_root_criteria tests` 只命中新测试文件，且其中 `test_the_worker_context_package_carries_the_block` 是**手工** `_seal({...})`，不经过 `_decide`。
- 我用临时脚本（仿 `test_output_port_claims._leaf_intent`，monkeypatch `carried_root_criteria_for` 返回一条链接）确认接线本身**是通的**：`## carried_root_criteria` 段以 `data_not_instruction=True`、`version=carried-root-criteria-v1` 出现在 worker intent 的 message 里。所以是测试缺口，不是代码缺陷。
- 建议：在 `test_output_port_claims.py` 旁加一条走 `_decide` 的测试，用 `plan.goal` 夹具里带链接的 review 叶子（或 CodeWorld 的 verify 叶子）断言 `_section(message, "carried_root_criteria")["criteria"] == carried_root_criteria_for(...)`，并断言无链接叶子的 message 里没有该段。

### P2-2 `covered_by` / `carries_root_criteria` 只按 criterion_id 聚合、不带 `root_task_id`，递归方法下会把嵌套层的链接算到根准则头上

- 位置：`root_review.py:1106-1165`（`by_task` 按 task 聚合后，`covered_by.setdefault(parent_criterion_id, …)`、`carries` 字典均不含 `parent_task_id`）；`carried_criteria_in_revision` 遍历**所有**已采纳实例，嵌套实例的 `parent` 是中间 compound 任务，其 `parent_criterion_id` 是中间任务的准则。
- 触发条件：`code.review-changes-recursively` / `appworld.resolve-entity-recursively` 这类递归方法，嵌套目标类型与根相同，准则 id 相同（`c-every-chunk-reviewed` / `c-entity-resolved`）。此时嵌套 `summarize`/`pick` 叶子的 `carries_root_criteria[].root_criterion_id` 与根的同名，并被并入根 `criteria[].covered_by`；评审员分不清哪条是根层的承诺人。今天种子方法的链接全部落在 primitive 步骤（我逐一列过 10 个方法），不会出现「链接落在 compound 上 → covered_by 为空」的情形；`CarriedCriterion.to_json` 与 Worker 块都带 `root_task_id`，只有请求包这两处丢了。
- 建议：`covered_by` 只收 `parent_task_id == 根 task_id` 的链接（或按 `(root_task_id, criterion_id)` 聚合并在条目里带 `root_task_id`）；`carries_root_criteria[]` 加 `root_task_id`。

### P2-3 `carries_root_criteria[].leaf_review_verdict` 是层门控的确定性盖章，不是对 `evidence_requirement` 的判断，v2 提示词未说明

- `criteria_for` 给每条叶子准则（含 `c-explained`）同一组 `required_check_ids=gates`，叶子 ReviewRecord 在验证层 PASS 时对 `c-explained` 也写 PASS——没有任何一方读过 report 是否「解释了为什么」。请求里把它标成 `leaf_review_verdict: PASS` 呈给根评审员；v2 硬约束 1 说「叶子 PASS 只对其承担的根准则有效」，容易被读成「这条 PASS 已经是证据」。测试里的脚本化评审员要求 PASS **且**摘录含指定文字，所以测试是对的，但真实模型不一定这样读。
- 建议：字段改名（如 `leaf_gate_verdict`）或在 `requirements_revision_semantics` 同层加一句「leaf_review_verdict 只表示验证层通过，evidence_requirement 仍须从 excerpt 判」。

### P2-4 第 4 条「变异自证」是空测

- `test_mutant_a_blank_revision_explanation_is_visible_in_the_request` 只 monkeypatch 后断言 `payload["requirements_revision_semantics"] == ""`，任何实现都通过；docstring 说「由 `test_the_revision_numbers_are_explained…` 抓」，但那条测试并不在该 monkeypatch 下运行。真正杀死该变异的是我的源码变异 M8（见 §3）。journal「4 条变异全部 KILLED」的口径应改为 3 条自证 + 1 条被既有断言覆盖，或把这条改成真变异。

### P2-5 摘录读取先整文件入内存再截断

- `excerpt_of` → `read_verified` 必须全量读以复核哈希，所以 4096 上限不减少 I/O 与内存；一个几百 MB 的交付件（例如 verify 步误把日志整份交付）会被整个读进内存并解码。`artifact.size_bytes` 已在 header 里，可在读之前用它做「超过 N MB 直接 `omitted`+size」的预筛。非阻断。

### 已核对、无缺陷的点

- (a) `excerpt_of` 异常面：`get_artifact` 缺件返回 `None` → `unavailable`；`read_verified` 的 `storage_uri` 空 / 缺文件 / 符号链接 / 非常规文件 / 权限 / hash 不符全部收敛为 `ArtifactStoreError`（`open_nofollow` 把 `OSError` 转成它），`handle.read()` 的 `OSError` 也被捕获；非 UTF-8 或含 NUL → `binary`；预算耗尽 → `omitted`。没有会打挂 `_advance_root_review` 的路径。请求 hash 稳定性：摘录是内容寻址字节 + 两个常量的纯函数；`list_acceptance_outputs` `ORDER BY producer_occurrence, output_port, source_revision, artifact_id`，`list_plan_memberships` `ORDER BY occurrence_id`，`list_method_instances` `ORDER BY created_at, instance_id`，`child_acceptance_refs` 已排序，`covered_by` 顺序由此确定；`unavailable.reason` 里的错误文本只含文件名（=content hash），不含随机路径。测试 `test_the_request_hash_covers_the_excerpt_and_is_reproducible` 覆盖同状态两读同 hash。
- (b) `criteria_for` 至少产出 1 条准则（`c-leaf-verified` 兜底），不存在「欠 0 条仍需评审」；`refines_parent` 步骤继承父 `requirement_refs` 但不再被读；多次 refinement / 同 method 多 occurrence：`carried_criteria_in_revision` 以当前修订的 `list_plan_memberships` 做 `task_of` 守卫，旧实例的 occurrence 不在其中即被跳过；根准则无人承担时 `covered_by=[]` 明示给评审员，系统不自填（`test_the_root_resolution_still_needs_the_reviewers_pass`；`_child_review`/`record_review` 未改，AER I05 保持）。计划提交阶段的 `root_coverage_gap` 仍保证每条根准则至少有一条链接。
- (c) AppWorld：`appworld/task_types.json` 所有 primitive 类型 `coverage_criteria` 为空，方法链接落在 `confirm`（`c-request-satisfied`）、`submit`（`c-actions-confirmed`）、`pick`（`c-entity-resolved`）；`profile` / `query` / `search` / `narrow` 叶子由「盖父准则 PASS」变为 `c-leaf-verified`。行为是收敛而非回归；`tests/` 无既有断言依赖旧形态（`git diff 8b8466d c9adf5b -- tests` 只有新增文件，全量绿）。Host 侧若有解析叶子 review.criteria 的逻辑需自查（本副本无 Host 代码）。
- (d) 除 P1-1 外：`fill_content_hashes` 只补引用；`patch` 端口仍被 verify 的 DataRequirement 消费，端口集合不变。
- (e) `ROOT_REVIEWER` 默认 = v2（`event_handler.py:7174/7206` 经 `_template` → `template_for_domain` 读 mission 冻结的 `prompt_versions`，旧 mission pin v1 仍走 v1）。C3 真实回复夹具只用于 `test_the_c3_package_before_the_fix…` 钉旧包形态；v2 包下的判定全部由脚本化评审员 `_evidence_reviewer` 给出（只认 `covered_by` 指向的贡献 + `leaf_review_verdict=PASS` + 摘录含指定文字），经 `_collect_root_review` 落 ReviewRecord；对照组 REJECTED、根 Resolution 不成。无系统自填。
- (f) `_new_mode` 18 == 18，见 §1。
