#### P0-2 · 同一个叶子第二次验收会在 `_witness` 里抛 `StoreError`，被上层吞掉 → 撤销后返工的路径整条不通

- 位置：`src/agent_orchestrator/orchestrator/leaf_acceptance.py:598-622`
  ```python
  witness_id=f"wit-{content_hash_of({'t': task_id, 'at': int(now_ms)})[:32]}",
  ...
  try:
      return self.semantics.get_validity_witness(witness.witness_id)
  except StoreError:
      self.semantics.insert_validity_witness(mission_id, witness)   # ← 这一句会再抛
      return witness
  ```
- 问题：witness_id 含 `now_ms`，唯一索引不含 `now_ms`（它是
  `(mission, consumer_kind, consumer_id, purpose=ACCEPT, scope_id, scope_epoch, support_revision)`）。
  于是「同一个叶子、同一个 epoch、同样的观察条数、不同时刻」的第二次验收
  会 mint 一个**新 id**、落在**旧键**上：`get_validity_witness` 查不到（id 不同）→
  走 `except` → `insert` 撞唯一索引 → `StoreError` 从 `accept()` 抛出去。
- 后果：`event_handler._accept_hierarchical_leaf`（`event_handler.py:2197-2199`）
  捕获 `(ContractError, ResolutionCommitRejected, StoreError)` 并只记一句
  `acceptance refused`。所以：**一个 Acceptance 被 revoke 之后重跑该叶子，
  新的 Acceptance 永远写不进来**（除非期间恰好新增了一条观察或 epoch 动了），
  而 `_require_accepted_work` 又要求「每个活的 primitive occurrence 都有 CURRENT Acceptance」
  → Mission 再也判不了。这条和 P0-1 是同一个根因（自造 witness id vs. 语义唯一键）。
- 证据：探针 `test_probe_a_second_acceptance_of_the_same_leaf_cannot_mint_its_accept_witness`
  实跑，第二次 `_witness(...)` 确实 `pytest.raises(StoreError)`。
- 建议：`_witness` 的 witness_id 不要含时钟（含 `(task, purpose, scope, epoch, support_revision)`
  就够，正好等于唯一键），或者把 `insert` 的冲突按「键被占」处理并回读该键上的行。
  顺带：现有 `except StoreError: insert(...)` 这个写法本身就是把「查不到」
  和「插不进」混成一件事。

## 四、总体结论

**需修后合。**

必须先处理的两条，都在 2c 新增的许可链上，都是**沉默的永久性活性缺陷**：

- **P0-1**：DATA 许可与前置条件许可共用 `purpose=START` 与同一个
  `support_revision` 计数器，先到先得 ⇒ 「既消费数据、又在 gated 方法之下」的叶子
  永远拿不到 START 许可、永远不派发。这不是偶发碰撞，是构造性的。
  实施方正在写的迁移 18 `subject_digest` 看起来就是正解，
  **但那份工作不在本次审阅的 `d26a7b1` 里**——要么带上它一起合，
  要么把这条明确写进 HANDOFF 的已知缺陷。
- **P0-2**：`LeafAcceptanceAssembly._witness` 自造的 ACCEPT 见证 id 与
  `validity_witnesses` 的语义唯一键不同源，同叶子第二次验收抛 `StoreError`
  并被上层吞掉 ⇒ 撤销后返工整条不通。与 P0-1 同一根因。

应在本片或第三部分开工前一并处理的：**P1-3**（F5 的接线零测试，
且交付回执分支在整套里从未执行）、**P1-4**（取证封顶无测试且与 I19 矛盾）、
**P1-5**（端口子串误配）、**P1-6**（能力表 fail-open）、
**P1-7**（`latest_requirements_revision` 被叶子链改写）、
**P1-8**（提示词 pin 可以选到与包不匹配的版本）。

**性价比最高的一条**：把 §17/§18 的 START-lane 场景从 `Env` 测试替身
搬到真的 `build_planning_world` 上（P2-16）。
P0-1 之所以能在 2373 条绿测试下存活，直接原因就是替身的
`snapshot().support_revision` 恒为 1；换成真世界之后，
P0-1、P1-4、P2-11 三条会同时暴露。

需要肯定的是：上一轮点名的 F1、F7、F6(3) 三条最重的都真修了，
F2/F3/F4/F5(函数部分)/F8/F10/F11/F12/F16 也都是真修 + 行为级证据；
「取证只读、UNAVAILABLE 绝不落记录」这一块（5 条杀手）是本片写得最干净的部分；
2c §4.6 的 `HierarchicalMissionStalled`「只记录、不判决」的取舍我完全认可，
它是把这类沉默停滞变成可运维事件的正确方向——只是 P0-1 这一条，
它记下来的会是一条**永远不会自己解开**的 stall。
