## 2. 重点审查

### (a) 同哈希过滤只对只读叶；accepted 只计当前 plan —— 不让 P2.3m 失效；P2.3q 复用仍正确

收集处 `event_handler.py:5474-5486`：`drop_same_hash` 仅当 `read_only_leaf(binding)`。写型叶列出或改写的文件一律登记，即使哈希等于已验收产物。

`_accepted_path_hashes`（`:8457-8485`）先取 COMPLETED，再与当前 `network.occurrences` 的 `task_id` 求交。退役方法的 apply 不再阴影替换叶。

- **P2.3m 防只读叶重放补丁**：只读路径未改。同哈希仍从 recorded 丢掉，P2.3o `bound_artifacts_named_in_envelope` 仍把绑定输入加回 `rule_check`。`read_only_rewrites(..., accepted=)` 仍用这张表：当前 plan 已验收的同哈希不算新写。退役叶的哈希**不再**豁免只读改写（比原来更严），被拒方法不能借只读叶把旧字节登记为本叶产物。
- **借道回流**：新 apply 的工作区从 seed + **绑定**输入起步，退役 apply 不是绑定生产者，旧 `net/retry.py` 不会自动出现在盘上。要登记必须由本叶写出。这是 M2-r1 的预期修法，不是 store 偷运。
- **P2.3q 复用只读叶**：`share_active` 的 facts/reproduce 保持同一 `task_id` 且仍 COMPLETED，落在当前 plan 成员里，accepted hashes 仍计入。overlay 走绑定生产者，不靠这张表。

变异 M4（`drop_same_hash = new_mode is not None`，写型也丢同哈希）**SURVIVED**：方法切换 e2e 仍绿，因为当前 plan 过滤已去掉退役哈希。说明 M2-r1 形状上「只计当前 plan」已足够；「只对只读叶丢同哈希」是防御纵深，本片 e2e 没有单独钉住。

### (b) 套用 unified diff —— 单文件绿；多文件静默半套；失败不具名

`_record_applied_diff_files`（`:8487-8538`）只对写型叶、只对 `.diff`/`.patch`，把 `files_patched_by_unified_diff` 的结果 `put_bytes` 成带 `artifact_id` 的产物。随后走同一 overlay（路径在 seed 上则预铺；P2.3t 写型 `tests/` 进 overlay；P2.3u 只读新写 `tests/` 不进，`test_overlay_drops_new_tests_written_by_a_read_only_leaf` 绿）。登记发生在 `workspace.snapshot` 的 missing 检查之后：信封点名但未落盘的源码仍 `envelope_invalid`，diff-only 路径依赖信封只点名 diff/报告。

单文件套用：`test_c3_unified_diff_patches_the_seed_window` 与 diff-only e2e COMPLETED，绿。

**解析缺陷**（P1-1）：`_parse_unified_diff`（`bound_workspace.py:157-165`）遇到下一个 `--- ` 时没有把当前 hunk `body` 刷进 `hunks`，多文件 diff **只保留最后一个文件**。独立探测：两文件均能套用的 unified diff，结果只有 `other.py`。上下文不匹配时 `_apply_hunks` 对**该文件**返回 `None`（单文件内不半套），但多文件仍可能「最后文件成功、前面全部丢掉」。`../` 与绝对路径因不在 seed 键上被 skip；二进制 `read_text` `UnicodeDecodeError` 也 `continue`（`:8508-8511`）。全部是静默跳过，没有具名 `ResultRejected`。与任务书「必须 fail-closed 且具名，不能静默半套」不符。

### (c) 相同失败指纹 —— M3 的 21 次会被判相同；`code_test` 过粗；N=3 非常量配置

`verification_failure_fingerprint`（`occurrence_tasks.py:449-471`）：`layer` + `detail.problems`（json 排序），否则 summary；去掉 `\bin 0.06s\b` 与 `/workspaces/<id>/`。N=3 来自 `MAX_IDENTICAL_VERIFICATION_FAILURES`（注释：比只读改写上限 2 多一次），不是配置项。计数是同一 occurrence **末尾连续** attempt（`:8701-8717`），含当前次。第 3 次取消该叶并 `PlanningRejected{repeated_verification_failure}`。attempts 如实（e2e `apply_attempts==3`），预留释放、守恒成立。

只读证据：

- M2-r1：42 次 VerificationFailed 全在新 apply `task-ec5b…`；41× `rule_check` 同一 `problems=["artifact 'net/retry.py' is not a recorded workspace file"]`，attempt-33 一次 `code_test`「4 failed, 2 passed, 2 skipped in 0.05s」打断连续串。新码下登记修复后这 41 次 rule_check 不应再出现；若仍出现，第 3 次就会升级，到不了 42。
- M3-r0：21× `code_test`，无 `problems`，summary 仅 `pytest failed: 1 error in 0.06s|0.07s|0.08s`。去时序后指纹相同，第 3 次升级。**早停对 M3 有效。**

过粗（P1-2）：`code_test` 的 summary 是 stdout 末 300 字的最后一行，真实局就是 `1 error in 0.06s`，**不含** SyntaxError 正文。任意两次「1 error」的不同异常（SyntaxError → ImportError）会判相同，过早升级。`2 failed` 与 `1 error` 能分开。

与 P2.3m/u/s：**不双触发**。m 走 `ResultRejected{read_only_leaf_rewrote_workspace}`；u 走工具层 `read_only_existing_file` / `read_only_leaf_kept_writing`；本片走 `VerificationFailed`。s 的 reconcile 在只读升级里有调，本片 `_escalate_repeated_verification` **没调** `reconcile_retiring_instance`（P2，依赖 s 的 Deferred）。

修复上限：`MAX_IDENTICAL_VERIFICATION_REPAIRS=1`。第一次 N=3 → PlanningRejected，空转见 `rejected_refinements` → **`planning_failed`**（`:2204-2230`，合入口径）。同一 Mission 再有一叶 N=3 时 `used>=1`，直接 `fail_mission(NO_DISPATCHABLE_WORK)`（`:8775-8778`）。与 journal 合入「其他修复受阻 → planning_failed」及 P2.3s「不得 `no_dispatchable_work`」不一致（P1-3）。detail 仍带 `repeated_verification_failure`。
