## 2. 重点审查（P0/P1 逐条）

### (a) streak 键 / 清零 / 瞬时错误 / 与 P2.3l·f·j —— ✅ 不是误杀 1 次 UNKNOWN

键是 **Mission 级进程内计数**：`self._after_handoff_zero_streak[mission_id]`，另用 `self._counted_after_handoff_unknowns`（invocation_id）防同一 UNKNOWN 被 poll 加两次。不是 per-ordinal、不是 durable 事件。`_count_zero_token_after_handoff`（`event_handler.py:1312-1345`）只扫 **当前 intent 的 agent_id** 上 `state=unknown` 且 `error_code==provider_error_after_handoff` 且已 `handed_off_at` 的行；0 token 则 +1，`usage.total_tokens>0`（或 input+output>0）则清零。

成功清零：planner / synthesizer / root_reviewer 走 `_collect_plan`，Worker 走 `_collect_attempt`，`AgentTurnState.COMMITTED` 时 `_reset_after_handoff_unknown_streak`。变异 M3 把 N 改成 1 → 第一次 UNKNOWN 即 `runtime_unavailable`，恢复测红，说明 N=2 才放过瞬时 1 次。

与既有梯子：

- **P2.3f**：streak&lt;N 时仍等 `min(stall_seconds, 300)`，planner 重交接一次；Worker **不**重交接（`done < MAX_SERVICE_REHANDOFFS and intent.kind != "attempt"`）。达 N 时 **跳过等待** 直接 give_up。synthesizer / critic `_is_planner_service` 为假，自身不走快失败，仍 P2.3f 收口（UNANSWERED / runner 门）。
- **P2.3l**：`_planning_rejected` 在开下一 ordinal **之前** 拦截 `provider_outcome_unknown` + streak≥N，直接 `_fail_runtime_unavailable` 并 return。梯子烧尽那条 `fail_planning(RUNTIME_UNAVAILABLE)` 不会再跑；`_fail_runtime_unavailable` 对已 TERMINAL 的 Mission 是 no-op。不是双写。
- **P2.3j**：修复轮看的是 `root_review_rejected` / `read_only_leaf_needs_write` 等，不是本 reason。不会被本片抢先开一轮修复。

C2 r0 在新代码下的推演：planner:1 + synthesizer COMMITTED（streak 清零）→ planner:2 第一次 0-token UNKNOWN（streak=1，等 300 s）→ 重交接 → 第二次 UNKNOWN（streak=2）→ `PlanningRejected{provider_outcome_unknown}`（仍先落事件）→ `_fail_runtime_unavailable` → `fail_planning(..., stop_reason=RUNTIME_UNAVAILABLE)` + `MissionFailed`，**不开 planner:3/:4**。不会停在 PLANNING 且 `stop_reason=null`。

### (b) 停机：原因 / 预留 / 守恒 / 不停 PLANNING —— ✅

`_fail_runtime_unavailable`（`7152-7182`）：先 `_release_mission_unknown_grants`（PENDING/CLAIMED/AGENT_CREATED/SUBMITTED/FAILED 上该 Mission 的 intent，调 P2.3l 的 `release_held_grants`），PLANNING 走 `fail_planning`、否则 `fail_mission`，stop_reason 都是 `RUNTIME_UNAVAILABLE`，再 `_release_mission`。Planner 路径经 `_give_up_blocked_plan_intent` → `_planning_rejected`（reason 如实 `provider_outcome_unknown`，detail 带 `consecutive_after_handoff_unknowns`）。Worker 路径 `_stop_consecutive_after_handoff_unknowns` 对 Attempt `settle_subject_known` + `mark_attempt_lost(provider_outcome_unknown)`，未知用量留账、不按 0 结算（P2.3l P1-1 同口径）。

梯子仍有 rung 的 e2e：`FAILED` / `runtime_unavailable` / `MissionFailed` / `open==[]` / grants 不在 HELD / `conservation.holds` / `reserved==0` / `planner_calls==2` 且无 `:planner:2`。

### (c) Worker `_observe_liveness` 不误杀长任务 —— ✅

`_provider_blocked`（`6884-6898`）只认 wait blocker `kind=="provider"`（ReAct 对 `ProviderInvocationUnknownError` 写下的 `RecoveryKind.PROVIDER`）。`provider_slot_wait` / `provider_response_wait` 明确排除——真在跑或只是排队的叶不算。stall 条件仍是 `running and not blocked`。Attempt 不重交接；第一次 UNKNOWN 等 P2.3f 窗后 `_give_up_blocked_attempt`（该 Attempt 计入 `attempt_count`，`max_attempts` 可再开一次）；第二次达 N 才 Mission 停。Worker e2e：`worker_calls >= N`、守恒、无悬挂 intent。

### (d) 诊断字段不落响应体/头/密钥；审计白名单不变 —— ✅

`_handoff_unknown_diagnostics` 只写 `type(exc).__name__` 与 `status_code`（int 且非 bool）。`_settle_unknown` 再按 `isidentifier` / int 过滤后并入 `usage_json`。单测 + e2e 断言无 `scripted transport loss` / `Authorization` / `api_key` / 异常 body。`audit_error_code` 与 `SDK_AUDIT_ERROR_CODES` 零 diff。

### (e) legacy —— ✅ 与基线一致

`_resolve_provider_blocked_service` 在 `_new_mode is None` 时直接 return（P2.3f 原门）。新对照测：同样 `_unclassified` 两次，legacy 不停机、不重交接、planner 只调 1 次、intent=SUBMITTED。golden / 旧函数 hash / 旧模式 560/13/0。

## 4. P2

- **P2-1** streak 与 `_counted_after_handoff_unknowns` 是进程内存。`_count` 只看当前 agent。进程在重交接后、give_up 前重启：当前 agent 只有 1 条 UNKNOWN → streak=1；`rehandoffs_of` 是事件（durable）已达上限 → 不再重交接 → `_planning_rejected` 会开下一 ordinal。单进程验收局（C2）不受影响；与 P2.3f 的 in-memory 等待窗同族。
- **P2-2** 计数是 Mission 级。synthesizer/critic 的 UNKNOWN 会加 streak，但它们自己不快失败；两片并行 Worker 各 1 次 UNKNOWN 会凑满 N=2。声称即「同一 Mission 连续」，不是 per-subject。
- **P2-3** 「有 token 的 UNKNOWN 仍走 P2.3f」在编排侧有分支，但 `settle_unknown` 对 after-handoff 异常只写 `{"budget": unknown}` + 诊断，**不从异常抄 usage**（journal §2r 未做已承认）。该路径实际上靠 COMMITTED 清零。无「带 token 的 UNKNOWN」e2e。
- **P2-4** Worker 不重交接，同一 Attempt 通常只有 1 条 UNKNOWN；达 N=2 需要第二次 Attempt。`max_attempts=1` 时不会走到 Mission 级 `runtime_unavailable`，但仍会在 P2.3f 窗后丢掉该 Attempt（不再 blocked 到墙钟）。Grok 叶预算一般 &gt;1。
- **P2-5** `_release_mission_unknown_grants` 不扫 SETTLED intent。成功轮的 grant 已在 COMMITTED 路径结清；本片 e2e 守恒绿。
- **P2-6** 字面命令 `pytest tests -k "execution or dispatch or audit or provider"` 会扫到 `gap_phase1` / `simple_harness_memory` / 缺 `asyncio` marker，收集期中断；收窄 ignore 后 55 failed 全是既有 schema v7≠v10、shared-capacity extra、atomic-decision 计数，**无一落在本片文件**。dispatch 定向 98 passed。
