## 2. 重点审查（P0/P1 逐条）

### P1-1（N3 / I05）两条 criterion-linked 叶写同一路径时，交付树丢弃评审员据以裁决的那份产物

- 位置：`src/agent_orchestrator/orchestrator/event_handler.py:7576-7671`（`_hierarchical_judgment_inputs`，`weight = (linked, rank, port)`）
- 事实（真实局 C1-r1，`H-L3-C1-r1/orchestrator/orchestrator.db`）：合成方法 `criterion_links` 把 `c-test-passes→verify`、`c-change-explained→summarize` 两步都标为 linked；`verify` 的 `report` 端口产物 `artifact-6a39796d223c2376` 与 `summarize` 的 `summary` 端口产物 `artifact-ee187756ce87cda0` **都是 `REPORT.md`**（v5 / v7，内容不同）。新裁决树：两者 `linked=1`，按 `accepted_at_ms` 后者胜 → 交付树里的 `REPORT.md` 是 summarize 的 v7；根评审员对 `c-test-passes` 的 ACCEPT 是读 verify 的 v5 摘录作出的（P2.3h `covers_root_criteria`），这份产物不在交付树中，`ArtifactMergeNotApplicableUnderHierarchical.superseded` 只记 `superseded_task_ids`，不记被压掉的 artifact id / content_hash。
- C3-r0 本身不受影响：`REPORT.md` 4 个写者中只有 verify（task-9fc3…）linked，且它也是最后验收、也是端口产物 → 树保留 `artifact-75e85d2f544f49dd`，**等于根评审包 `accepted_outputs[port=report]` 那份**；`stats/window.py` 四份 hash 相同。新树对 C3-r0 的交付 = 评审所见，✅。
- 但对合成方法（N1 正是要让合成器多产这类「verify + summarize 双 link」方法），「后验收者胜」会系统性地用 summarize 的 REPORT.md 覆盖 verify 的 REPORT.md。Mission 级 `file:REPORT.md` 仍 met，所以结果不变，但「交付与评审所见一致」在被 link 的证据文件上不成立。
- 建议修法（不自行修）：(a) 在 P2.3h 端口索引/验收侧把「两个 criterion-linked 端口产物落到同一 `source_identity.path`」视为计划缺陷——编译期拒绝或验收期 `PORT_PATH_COLLISION` 拒绝第二份，而不是在裁决树静默覆盖；(b) 至少把 `superseded[]` 扩成 `{path, kept_task_id, kept_artifact_id, kept_by, superseded: [{task_id, artifact_id, content_hash, linked, port}]}`，并在两个 linked 写者相争时把 `kept_by` 记为 `acceptance_order_between_linked` 让读者看得见；(c) 权重改 `(linked, port, rank)`，让评审员读过的端口产物优先于同叶/他叶的非端口 `accepted_artifacts`（不解决双端口同路径，但收窄 I05 面）。
- 复现：用 `_CodeWorld(method=_rebound(_c1_method()))` 让 verify、summarize 各写 `REPORT.md`（不同字节）并依次验收，跑 `_run` 到 COMPLETED，断言树中 `REPORT.md` 的 artifact 等于根评审包 `c-test-passes` 所引摘录的 artifact——当前实现会失败。

### P1-2（N4）「只读叶」按类型声明判定、运行时不强制，且把承担 `c-test-passes` 证据的 `verify` 叶也剥掉了 `code_test`

- 位置：`src/agent_orchestrator/orchestrator/occurrence_tasks.py:297-350`；`tests/orchestrator/full_target/test_read_only_leaf_policy.py:158-174` 明确断言 `verify` 无 `code_test`。
- 事实：诊断报告 N4 只说 `facts` / `reproduce`；P2.3k 把规则推广到所有 `external_read` 类型（`code.verify-tests@1` 是 `external_read` + `tests.run`），于是 verify 叶默认策略变为 `format_check, rule_check`。真实局里叶子 `success_criteria = ["c-test-passes","c-change-explained"]`（Host 的 RequirementsRevision 没有 `pytest:` check id），Mission 级 `success_criteria = ["file:REPORT.md"]`，所以 P2.3k 之后整局唯一跑测试的确定性层只剩 `apply-patch` 叶的 `code_test`；而 C3-r0 的 artifacts 表证明「只读叶」确实写产品代码（`stats/window.py` v1 由 facts 叶、v2 由 reproduce 叶写出），verify 叶（linked，赢下它写的每条路径）在 N3 新树里对 `stats/window.py` 也是最终写者（v4）。只要 verify 叶改了产品代码，交付树里这份代码不再被任何 `code_test` 度量。
- 运行时没有任何读写强制：grep `read_only|side_effect_kind` 在 `hierarchical_dispatch.py` / `commit_service.py` / `accepted_outputs.py` 为零命中；Worker 在只读叶照样持有 `workspace_write_file`。
- 建议修法：(a) 最小改动——承担 `criterion_links` 的叶（`carried_criteria` 中的 `task_id`）不适用只读豁免，或把 `tests.run` 能力视为「可被 code_test 度量」但对 `reproduce` 这类以红基线为目的的类型另加 `expects_red_baseline` 声明；(b) 更完整——验收侧对只读叶拒绝声明端口以外的产品文件写入（或裁决树只把只读叶的**端口产物**放进树，不放 `accepted_artifacts` 全集）；(c) 至少在 CHANGELOG/journal 写明「verify 叶失去 code_test」是有意扩大，并给 Host 加 `pytest:` check id 的建议。

### P1-3（N2）`goal_parameters` 把工作区绝对路径带进根评审包与 `context_version`

- 位置：`src/agent_orchestrator/orchestrator/root_review.py:1102-1106, 1225-1226`。
- 事实：真实局根绑定 `typed_parameters.repository = "/Users/taiwan/PROJECTS/SimplaHarness/simple_harness/.local-test-evidence/.../H-L3-C3-r0/worktree"`（`task_semantics` 表）。P2.3k 前的根评审包（C3-r0 `dispatch_intents` 里 root-review 意图的 `config.message.content`）绝对路径计数 **0**；P2.3k 后该路径原样进入送给模型的 JSON、进入 `content_hash`/`context_version`、进入事件与夹具（夹具 `SOURCE.md` 自己承认要把它改成 `<worktree>`）。后果：同一 Mission 状态在两台机器上的包 hash 不同（跨机重放/对照失效），主机文件系统布局泄露进模型提示与遥测。
- 「同一状态两次裁包 hash 相同」在单机上仍成立（探针 `test_root_review_request_hash_is_stable_across_two_builds` 通过；`content_hash_of` 走规范 JSON）。
- 建议修法：进入包前对参数做与 P2.3h 摘录同样的去标识（绝对路径 → `<workspace>` 或 workspace 相对标识；或只带白名单参数如 `failing_test`），并在 `RootReviewRequest` 文档写明「参数不得含主机路径」；Host 侧同步改 `repository` 绑定为工作区标识。
