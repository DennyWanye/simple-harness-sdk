## 2. 重点审查（P0/P1 逐条）

### (a) P2.3n：APPLICABLE 依据 / `synth:{n}` / 上限 / 替换共享 —— ✅ 不是无条件放行

`method_applicability`（`hierarchical_dispatch.py:2889-2948`）对每个仍开放（或修复轮点名）的 compound × 库方法调用 `assess_method`（`applicability.py:494-557`）。四轴顺序未改：TYPE_ERROR → CAPABILITY_UNAVAILABLE → PRECONDITION_FALSE → CONFLICT → NEEDS_EVIDENCE，否则 APPLICABLE。空 `applicable_when` → `all_truth(())` 为 TRUE → APPLICABLE，这是 §18.3 既有合同，不是本片旁路。被 `rejected_method_refs` 打掉的方法仍 `continue`，不进适用性（理由在 `rejected_refinements`）。

`goals_needing_method`（`3242-3248`）**显式跳过** `entry.report.applicable`，合成判断仍只计拒绝，避免「全是 APPLICABLE 却看起来谁都不适用」再开一轮。`test_repair_and_synthesis_bounds_are_not_relaxed` 钉 `PlanningRejected{root_review_rejected}` 恰好 1 次、无准入合成。`MAX_SYNTHESIS_ASKS=2`（`event_handler.py:276`）未改。

评估键（`3028-3041`）：`synthesis_round<=1` 保持 `{mission}:{revision}`；n>1 才 `{mission}:{revision}:synth:{n}`。事件类型仍是 `MethodApplicabilityAssessed`，与 P2.3i 的 `MethodSynthesisReplyRejected` / `MethodSynthesisReplyUnreadable`（按 ordinal）和 P2.3j 的 `PlanningRejected` 不共享键空间。P2.3j `repair_round_answered` 为假时不开合成；P2.3i 重问发生在合成收集内、不写适用性事件。未见双触发。

注意：Planner **包**每次从 live `method_applicability()` 组装，不读该事件。`synth:{n}` 主要防 G1/Host 把同 revision 的第二次评估当 no-op。变异 M2 去掉后缀后，e2e 采用测试仍绿，只有「新记录」测试红——键是审计钉，不是采用路径的唯一承重。

## 5. C2 停摆诊断（只读；建议不实现）

证据：`H-L3-C2-r0` / `H-L3-C2-r1` 的 `orchestrator.db`（`mode=ro&immutable=1`）+ 同目录 `execution.db` / `result.json`。

| 局 | Mission | 终态 | 最后关键事实 |
|---|---|---|---|
| r0 | `mission-3e9d9aec6dd186f0` | **PLANNING**，`stop_reason=null` | planner:1 + synthesizer 成功准入 `code.fix-by-reproduce-patch-verify-explain`；其后 planner:2/3/4 的 invocation 全部 `state=unknown`、`error_code=provider_error_after_handoff`（0 token）。每轮 P2.3f：等 300s → 重交接 → 再 UNKNOWN（后续约 7ms）→ `PlanningRejected{provider_outcome_unknown}` → **新 planner ordinal**。最后 `planner:4` intent=SUBMITTED，grant=UNKNOWN，预留 50000 未释放。`result.json` `budget_conserved: false`。距 `max_runtime_seconds=1800` 还差约 2 分钟时日志停更 |
| r1 | `mission-432c8aa1a2db8d24` | **FAILED** `budget_exhausted`（elapsed 1800.001，dimension=runtime） | 规划/合成/两叶验收成功；第三叶 `task-c67f931a…:attempt-1` Worker turn 3 同样 `provider_error_after_handoff` UNKNOWN；心跳 `blocked=true` 直到墙钟。该 Attempt 预留 100000 仍 RESERVED |

判定：**主因是 provider 侧在 handoff 之后抛了未归类异常**，不是 P2.3n/o 的适用性/预铺。`dispatch.py:657-659`：`_DEFINITE_PROVIDER_FAILURES`（含 401/402/429/5xx/timeout 映射）走 `settle_failed(exc.code)`；其余 `BaseException` 一律 `_settle_unknown(..., "provider_error_after_handoff")`。因此 **不是** 可见的 HTTP 500/502——若是，应落 `provider_server_error` + FAILED。鉴权探测正常与「handoff 之后才爆」相容。

运行时缺口（基 2845b7e 已含 P2.3l，但 P2.3l 的 `RUNTIME_UNAVAILABLE` 针对「从未到达模型」的 0 token UNKNOWN）：本两局 `handed_off_at` 已写，走 P2.3f 梯子；after_handoff UNKNOWN **不会** 停 PLANNING，而是新 planner 轮或 Worker 空转直到 1800s。r0 甚至没写 `MissionFailed`。预留在 UNKNOWN grant 上悬挂。这不是计数器/合成上限错误。

「只存 `error_code_hash`」：公开审计 `audit_error_code`（`execution/audit.py:83-84`）只放行 `SDK_AUDIT_ERROR_CODES` 白名单明文；`provider_error_after_handoff` **在**白名单，本两局 `provider_invocations.error_code` 列即为该字符串。缺的是 **HTTP `status_code` / 异常类名**（`ProviderError.status_code` 有槽位，execution 层不落库）。

建议（不实现、不改 contracts 亦可）：在 `provider_invocations` 或 usage_json 增加可选 `http_status: int | None` 与 `error_class`（异常短名），**不写响应体、不写密钥**。编排侧对「handoff 后连续 UNKNOWN 且 0 token」考虑有界 `runtime_unavailable`（与 P2.3l 的 before-handoff 对齐），避免 r0 那种 PLANNING 无 `stop_reason`。属后续片，不挡 P2.3n/o 合入。
