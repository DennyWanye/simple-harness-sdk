## 4. 交互与有界性

**计数互不污染（代码 + S-A/S-B 证据）：**

- `_synthesis_credits`（L4075）只数 `MethodSynthesisRoundRecorded{admitted:true}`：重交接不写该事件；收口写 `admitted:false`；重交接后成功写一次（键 `mission:goal`，幂等）→ 恰好一级。
- `_planning_attempts` / `_planning_ladder_spent`（L4090–4100）只数 `PlanningRejected`/`TaskGraphRejected`：重交接不写；收口写一条（ordinal 键）→ 恰好一次拒绝。
- D5-A：`_root_review_repairs` 只数 `reason == ROOT_REVIEW_REPAIR_REASON`，`provider_outcome_unknown` 不算修复轮；修复轮的 planner 意图两次未知 → `_planning_rejected` → Mission ACTIVE 分支按普通梯子上行或"committed plan stands"（与 P2-3 口径一致）。
- D5-B：`_refinement_round_asked` 按 revision 从事件表判定，与重交接无关。
- Critic：收口 → runner `ContractError("critic did not answer…")` 直接抛出 `_run_critic`，**不进入下一 ordinal**（L6091–6096 不在 `continue` 的 try 内）。

**有界性（公式）：**

设一个 Mission 在 P2.3f 之前的服务类意图数为 N（planner 轮 ≤ `max_planning_attempts` + 合成积分 + D5-A/D5-B 每 revision 各 ≤1 轮再各自上梯子；synthesizer ≤ 每个缺方法目标 1 轮；root reviewer ≤ `MAX_ROOT_REVIEW_ASKS`=2 × 包数，包数受 `max_root_review_cuts` 限；critic ≤ `MAX_CRITIC_ATTEMPTS` × 验证次数）。则

- provider 调用数 ≤ N × (1 + `MAX_SERVICE_REHANDOFFS`) = **2N**；
- 每个意图的额外等待 ≤ 2 × min(`stall_seconds`, 300) s（一次到重交接、一次到收口）；进程重启每次最多再加一窗（`_service_blocked_since` 在内存）。
- 极端例：root review 一个包 = 2 ask × 2 次调用 = 4 次（S-F 实测 4）；一个 planner 轮 = 2 次 + 2 窗。

1. **预算口径与实际行为不符（文档级）。** `rehandoff_service_intent` docstring（"the reservation is only settled when no charge is unknown"）、`_resolve_provider_blocked_service` docstring（"keeps the reservation held, which is the honest count"）、journal §2h"预算口径"与 CHANGELOG 都暗示被弃执行器的 UNKNOWN 会让预留保持 held。实际：`usage_facts` 不把 UNKNOWN invocation 导入编排账本，`has_unknown_charge` 在 `src/agent_orchestrator` 内**无任何调用**，`_settle_service_if_known` 只看账本的 `has_unknown_usage` → 预留被**释放**。证据：仓库测试 1 自己断言 `BudgetReleased.settled_tokens == 150`（即已 settle）；S-A 里 planner:1 两个执行器都 UNKNOWN 时 `BudgetReleased{settled_tokens:0, released_tokens:4000}`。影响有界（每个服务意图最多 1 次未计入 Mission 账本的可能计费调用），runner 侧 `unknown_usage_calls` 仍如实计数，且修前同一 UNKNOWN 调用本来就不进账本（区别只是预留由"永远 RESERVED"变为释放）。建议：改注释与 journal 为实情；若要真正 held，需在服务路径消费 `bridge.has_unknown_charge(previous_agent_id)` 并写 `record_reservation_held`（那是新行为，另开片）。
2. **`_provider_blocked` 的 kind 判定未被测试钉住**（M03 存活 full_target）。进程内夹具里合法慢调用的 liveness 是 `blocked:false, blocker:None`（无 deployment capacity），所以 e2e 分不出 M03；自拟 S-G 那样的 `Liveness` 级单元断言（`provider_slot_wait`/`provider_response_wait` → False）能杀死它，建议补进 `test_service_intent_provider_blocker.py`。这条对 Grok 重跑有实际意义：真实通路会报 `provider_response_wait`，若被误判会把 121–163 s 的正常调用重交接。
3. **换 owner 重启 + 他人持租的 CLAIMED 意图 → `run()` 闲置返回**（S-C'，既有行为，S-C0 证明与重交接无关）。验收 runner 单进程一次 `run()`，不触发；写在这里供运维知晓：重启请沿用同一 owner 或等一个 `lease_seconds`。
4. **`sleep(0)` 防御未被钉住**（M02 存活）。journal 已自述为防御；可接受。若要钉，需在有进展周期内断言 runtime 回合任务能推进（当前 P2.3e 测试在守卫存在时靠 poll 让出即可通过）。

无需处理的等价变异：M10（幂等键 + 幂等创建已兜底）、M14、M16。
