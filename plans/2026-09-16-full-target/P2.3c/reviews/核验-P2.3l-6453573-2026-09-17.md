### P1-1（N5）释放 grant 后用量账本对「后来对上账」不诚实

- 位置：`src/agent_orchestrator/runtime/agent_worker.py:155-159`（`usage_facts` 跳过 UNKNOWN）；`event_handler.py:6693-6696`（give-up 先 `release_held_grants` 再 `_import_usage` 再 `_settle_service_if_known`，且只导入**当前** `intent.agent_id`）；`provider_budget_guard.py:866-868`（`rehanded` 分支 `RELEASED` 后 `continue`，**不**走后面的 `_observe_in_transaction`）。
- 事实：诊断建议 a 是「记入 unknown_usage **并**释放 reservation」。实现只做了后半。`has_unknown_usage` 在 grant 非 HELD 且 `imported_usage.unknown=0` 时为假，于是 `settle_subject` 按 **0 token** 收口。测试断言 `reserved==0` 与守恒，**不断言** `imported_usage` / `unknown_usage_calls`。
  - 第一次 UNKNOWN 的执行器在重交接后被换掉，give-up 的 `_import_usage` 读的是新 agent，旧 invocation 永不进 `imported_usage`。
  - 若 300 s 后对账把第一次请求改成 `succeeded`/`failed` 且带用量：grant 已 RELEASED，`recover()` 不再扫到它；即便仍 HELD，`rehanded` 分支也会在 observe 之前 `continue`。已知计费丢失。
  - Host 包装层的 `unknown_usage_calls` 仍读 SDK invocation=UNKNOWN（journal「未做」写的是这一层），所以 M3-r2 形的 Host 计数仍可能是 1；**Mission 账本** `settled_tokens` / `imported_usage` 则把它当成 0。
- `runtime_unavailable` **没有**「0 token」闸：只看 `reason == "provider_outcome_unknown"`。give-up 发生在两次未知之后，没有 succeeded 的 planner 回答，故对「Planner 从未被听见」成立；但若未知请求其实已计费，停机原因仍是 `runtime_unavailable`。属同一口径缺口的弱端。
- 建议修法（不自行修）：(a) 重交接/give-up 时对**旧** agent 的 invocation 若仍 UNKNOWN，写一条 `imported_usage.unknown=1`（占用 `usage_ref` 之前先确认不会挡住后续对账更新，或用可覆盖的 unknown 行）；(b) `rehanded` 若 `record.state in {succeeded, failed}` 先 `_observe_in_transaction` 再 RELEASE；(c) 显式释放后的 settle 不得把 unknown 当成 0——要么单独「释放预留、保留 unknown 标记」，要么对账完成后再 settle；(d) 测试加：第一次 UNKNOWN 随后对账为 5 000 token，断言 `imported_usage` 有该 `usage_ref` 且 `settled`/`unknown` 如实，守恒仍成立。
- 复现：现有 `test_provider_grant_rehandoff.py` 的 `_transport_loss` 永不对账，绿；在 fixture 里让第一笔 invocation 在重交接后变成 `succeeded` 带 usage，断言账本非 0——当前实现会失败。

### P1-2（N7 / AER I05）系统会在缺子叶准则名时自填 PASS；GoalResolution 不随 validity/epoch 失效

- 位置：
  - `composition_review.py:427-440`：系统写 `ReviewRecord(reviewer_agent_id="composition-reviewer", verdict=ACCEPT, official=True)`，AER 公式再读这个 ACCEPT。这是「系统写判决」。设计选择（诊断选项 a/b：按子叶验收机械合成）允许**不**开模型评审员，但 I05 的「只转录子叶已判定的准则」必须钉死。
  - `composition_review.py:533-537` **fallback**：子叶官方评审没有 `leaf_criterion_id`、但有任意 `PASS` → 父准则判 PASS。注释写「restating ACCEPT is not filling PASS」——这正是填 PASS。

  - `hierarchical_dispatch.py:1139-1152`：`resolved_tasks` 只滤 `verdict==ACCEPT`，**不滤** `validity==CURRENT`、不看 witness/epoch。epoch 失效或决议被撤回后，ORDER 仍视为 ACCEPTED。
- 生产路径（M3 `assess-by-reading` 链 `c-failure-reproduced → reproduce/c-reproduced`）：叶子 `criteria_for` 会把 `c-reproduced` 写进官方评审，结论碰巧仍对。变异 **M5**（去掉 fallback）e2e **仍绿** = 测试不覆盖这条 I05 洞，生产叶子也用不到它——但它是对「共享义务 + 缺名准则」的系统填 PASS。
- 子叶 REJECTED/REVOKED：无 CURRENT 验收 → `next_compound_phase` 停在 `waiting_children`，不形成决议，随后 `no_dispatchable_work` 有界。✅ 但没有「composition REJECTED 诚实停机」——`resolve_one` 在 `record.verdict is not ACCEPT` 时 `return None`，吞掉 `ResolutionCommitRejected`，看起来像 stall。测试零覆盖。
- 与 P2.3j retire/refine：共享义务的内层决议 `adopted=False`、不 SATISFY 根义务，被退实例离开当前网络后旧 `task_id` 不再被 `occurrence_outcomes` 扫到。✅ 主交互不炸。但旧 `GoalResolution` 行残留，且 `resolve_ready` 按 **任何** 历史 `goal_task_id` 跳过；validity 也不清。无测试。
- 根 `criterion_links` 指向子 compound：P2.3h 的根评审包按 **Acceptance.task_id** 填 `covered_by`。子 compound 没有 Acceptance（只有 GoalResolution），e2e 的 `c-root → assess/c-sub` 在真评审员看来 `covered_by=[]`。测试用脚本化评审员对包内准则一律 `met: True`，所以仍 COMPLETED。M3 构造 `root_requirements=null`、根评审次数必须为 0，**本层生产路径不踩**；测试自己发明的带根准则形状踩了。
- 建议修法（不自行修）：(a) 删掉 `_child_covers` fallback，只认 `leaf_criterion_id` 的 PASS，缺则 UNKNOWN、不形成 ACCEPT 决议；(b) `_accepted_children` / `_accepted_occurrences` 按 `(task_id, obligation_id)` 过滤，与 `occurrence_outcomes` 的 Acceptance 键一致；(c) `occurrence_outcomes` 只认 `validity==CURRENT` 且 witness 对当前 epoch 仍 USABLE 的 GoalResolution，P2.3j retire 时把被退实例的子决议标非 CURRENT；(d) 测试：子叶评审只有 `c-leaf-verified`、链接要 `c-reproduced` → 不得 GoalResolution；REVOKED 子叶不得决议；epoch+1 后 ORDER 收回；retire+refine 后旧子决议不在新网络。
