## 2. 构建方式

按 `docs/build-and-release.md`：主工作树保持干净（同期有只读消费者在用），构建在
`git worktree add --detach` 出来的干净分离工作树里做，**一次性**产出，之后不再 `uv build`。

```bash
git worktree add --detach "$BUILD_DIR" 05cfbb83a38d8342bf525992d56dab2491bba576
cd "$BUILD_DIR" && uv sync --frozen --group dev
uv run --frozen python scripts/build/reproducibility.py --output candidate --planned-tag v0.12.1
```

`reproducibility.py` 在 `SOURCE_DATE_EPOCH=0` 下**连建两次并逐字节比对**，通过后才落盘；
`candidate/` 即冻结发布集：wheel、sdist、`BUILD_INFO.json`、`SBOM.spdx.json`、`NOTICE`、
`SHA256SUMS`、`candidate-manifest.json`（schema `simple-harness-candidate-manifest-v1`）。

同一批字节复制进 `dist/` 后按手册补权威溯源并复验：

```bash
uv run --frozen python scripts/build/authoritative_provenance.py emit   --dist dist --source-commit 05cfbb83a38d8342bf525992d56dab2491bba576 --build-utc 2026-09-17T03:14:41Z
uv run --frozen python scripts/build/authoritative_provenance.py verify --dist dist --source-commit 05cfbb83a38d8342bf525992d56dab2491bba576 --version 0.12.1
uvx --from "twine>=6.1,<7" twine check dist/*.whl dist/*.tar.gz
./scripts/verify_release_gate.sh
(cd dist && shasum -a 256 -c SHA256SUMS)
```

## 4. 已知红项与归类（未修改任何门禁脚本）

**`mypy` 17 errors / 4 files —— 基线数字，不是本次引入。**
`plans/2026-09-16-full-target/HANDOFF.md` 从 P1.1 起每一片都记录「mypy 17（基线）」。
评测适配层缺可选依赖（`are.simulation.*`、`pydantic`、`agentdojo.*`、`deepseek_recipe`）
加上 `evaluation/agentdojo_runner.py:383` 的 `Trying to read deleted variable "error"`。
两者都在评测适配层，不进 wheel 的运行路径。

**`reuse lint` FAIL —— 长期既有缺口。**
本次在 `candidate/` 落盘之后跑，清单里多了 5 个构建产物；扣除后 **174** 个文件没有 SPDX
头且未被 `REUSE.toml` 的 `[[annotations]]` 覆盖。0.12.0 记的是 184（当时在构建前跑）。
同类既有缺口，不是 0.12.1 引入的。**替代证据**：许可元数据由 `NOTICE`（`af264702…`，
与 0.12.0 逐字节相同）与 `SBOM.spdx.json`（`1e4f4cdd…`）承载，两者都进了 `SHA256SUMS`
与 `candidate-manifest.json`；wheel/sdist 的 `twine check` 通过，包内 `License-Expression`
为 Apache-2.0。

**全仓 `pytest -q` 的收集错误 —— 全部是环境缺口。**
手册第 2 步的裸 `pytest -q` 在本机会被收集错误打断（`Interrupted`）。口径与 0.12.0 相同：

- 若干文件用 `@pytest.mark.asyncio`，而 `pytest-asyncio` 不在 `[dependency-groups] dev` 里，
  `--strict-markers` 于是拒绝（`tests/orchestrator/gap_phase1/*` +
  `tests/integration/test_shared_capacity_dispatch.py`）。
- `tests/integration/runtime/test_context_use_*.py` 缺 `simple_harness_memory`
  （认知记忆 SDK 2026-09-10 已从产品线整条移除）。
- `tests/orchestrator/gap_phase1/test_agentdojo_*.py` 缺 `pydantic`。

补上这两个可选依赖后收集恢复正常。本次全仓用 `--continue-on-collection-errors`，数字见下。

### 4.2 从 0.12.0 留下的两条真实遗留（本次未修）

**F-REL-1 — `tests/unit/contracts/public-api.json` 的版本戳没跟上。**

### 4.4 一条环境陷阱：不要给全仓跑加 `pytest-asyncio`

与 0.12.0 相同：为了让 gap_phase1 能收集而加上 `--with pytest-asyncio`（1.4.0）之后，
本机会**永久挂起**。所以本次的编排范围门禁用 `--ignore=tests/orchestrator/gap_phase1`
而不是加插件；gap_phase1 要跑就单独跑、单独超时。

## 6. 消费者须知

- **默认语义未变**：`MissionSpec.orchestration_semantics_version` 默认 `legacy`，
  不传这个字段的调用方行为与 0.12.0 / 0.11.x 一致（legacy 事件字节 golden、
  旧函数源码 hash、`_ExplodingDispatch` 三例全绿）。
- **策略/配置快照又变了**：`OrchestratorConfig.to_json()` 与
  `policy_snapshot()["config"]` 多 `max_root_review_repairs` 键（默认 1）。
  0.12.0 的 digest `7cf60224…` 不再成立；外部对照脚本要重取基线。
- **分层 Worker 提示词**：新 Mission 拿 `worker-hierarchical-v2`（v1 保留可 pin）；
  AppWorld 分层拿 `worker-appworld-hierarchical-v1`。域档版本未变
  （`resolve_domain("appworld-v1").version` 仍是 `"3"`）。
- **分层 Mission 收尾会花两次 mission 账户的模型调用**：根评审人
  加上既有的 Mission Judge。预算按两次算。
- **PANDA/HDDL 后端在本机是 stub**：没有 cmake/gengetopt；配置 `SH_PANDA_PARSER`
  后真实用例自动启用。
- **L2 `appworld` 谓词的 `app` 参数受 `PUBLIC_READ_APIS` 限制**：非 `supervisor`
  应用的读取返回 `OBSERVER_UNAVAILABLE`（诚实的 UNKNOWN，不是假的 FALSE）。
- **库 schema 版本 18**：迁移 16/17 的校验和逐字节未动。
- **Grok 两臂验收重跑尚未完成**；**M3 共享复用依赖 P3.2 未并入**。
